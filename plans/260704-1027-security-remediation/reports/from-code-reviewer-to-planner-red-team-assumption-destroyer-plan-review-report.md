## Finding 1: H5's "mirror `ApplySettlement`'s tx pattern" is a false analogy — the two services write different tables and have incompatible multi-row semantics
- **Severity:** High
- **Location:** Phase 1, section "Architecture" (H5 bullet); phase-01 lines 19, 32; plan.md line 48
- **Flaw:** The plan asserts `FlexPaySettlementService.ProcessSettlementFile` can wrap its UPDATE+ledger writes in a single `db.Transaction` "mirroring" `SettlementEventHandler.ApplySettlement`. The two are not analogous:
  - **Tables written differ.** `ApplySettlement` (settlement_event_handler.go:214-430) writes `settlements`, `transactions`, `ledger_entries`, and `timesheets.revenue_paid` — one logical settlement per call, locked via `GetByIDForUpdate`. `ProcessSettlementFile` (flex_pay_settlement_service.go:53-188) writes `advance_payment_requests` (via `MarkReceivableSettled`), `transactions`, and `ledger_entries` — but it loops over MANY transactions (`for txnID, tx := range txnMap` at line 123) and **continues past errors** (lines 134-136 swallow the txn update error with `continue`; lines 159-162 swallow the ledger error with no return).
  - **Per-row vs all-or-nothing semantics differ.** `ApplySettlement` is one settlement → one tx, deadlock-retried. `ProcessSettlementFile` settles N transactions for N request IDs. If the cook wraps the entire loop in one tx, a single bad transaction ID rolls back all the others (correctness regression — partial settlement was the previous behavior). If the cook wraps each iteration in its own tx (the only sound choice), the plan's instruction is misleading because the reference (`ApplySettlement`) is per-call single-tx, not per-iteration.
  - **Idempotency models differ.** `ApplySettlement` idempotency key = "all linked timesheets already `revenue_paid`" (settlement_event_handler.go:241-258). `ProcessSettlementFile` has no timesheet linkage; its idempotency key is the file hash, which the plan correctly proposes but does not reconcile with the fact that `MarkReceivableSettled` (advance_payment_requests update) has its own idempotency semantics the cook must audit independently.
- **Failure scenario:** The cook follows the plan's literal instruction ("mirror ApplySettlement"), wraps the whole `for txnID, tx := range txnMap` loop in one `db.Transaction`, and a settlement file with 50 valid + 1 stale transaction ID now rolls back all 50 valid settlements on every retry — or worse, deadlocks because `transactionRepo.Update` inside the loop doesn't take a row lock the way `GetByIDForUpdate` does, so the deadlock-retry scaffolding copied from `ApplySettlement` retries a transaction that has no `FOR UPDATE` and the bug looks fixed in tests but manifests as write skew in prod.
- **Evidence:**
  - `flex_pay_settlement_service.go:99-173` (txnMap loop, two distinct swallow-and-continue paths at 134-136 and 159-162; success path returns `Success:true` regardless at line 181).
  - `settlement_event_handler.go:214-430` (single-transaction, `GetByIDForUpdate` at 261, deadlock retry at 411).
  - `flex_pay_settlement_service.go` does NOT import `gorm.io/gorm` (line 1-17 imports) — there is no `*gorm.DB` on the service struct (lines 19-26). The plan does not mention that adding `db.Transaction` requires changing the constructor signature AND the bootstrap wiring (`bootstrap/services/init.go:318`).
- **Suggested fix:** Replace the H5 architecture bullet with: "Wrap each `for txnID, tx := range txnMap` iteration in its own `db.Transaction` (per-iteration, not whole-file). Add `*gorm.DB` to `FlexPaySettlementService` and update `bootstrap/services/init.go:318` + `bootstrap/container.go:337`. Replace both `continue`/swallow paths with `return err` so the loop fails fast on the first unfixable row; surface the error in `SettlementResult.Success=false`. Use `GetByIDForUpdate` (not `GetByID`) for the transaction lookup to close the write-skew window. File-hash idempotency is independent of this; do not couple it to the timesheet `revenue_paid` model."

## Finding 2: H6's "in-flight dedup via 409" understates the actual existing dedup and mis-targets the key
- **Severity:** High
- **Location:** Phase 1, section "Architecture" (H6 bullet); phase-01 lines 20, 34; plan.md line 49
- **Flaw:** Two linked false assumptions:
  - **(a) "The execute worker is not idempotent."** It IS partially idempotent. `DisbursementExecuteWorker.ProcessJob` (disbursement_execute_worker.go:99-122) calls `walletPaymentService.Initiate`, which (i) checks `HasPendingForRecipient` (wallet_payment_service.go:163-169) by `recipient_account_no + recipient_bank + provider` and rejects with `ErrDuplicatePaymentInProgress`, and (ii) on duplicate `request_id` unique-index violation, returns the existing row (lines 199-209). The worker then re-checks `row.Status != StatePending` and exits (lines 118-122). So a duplicate `RequestID` for the same recipient IS caught downstream — but each retry mints a NEW `RequestID` (`GenerateTransactionCode(true, true)` at retry_disbursement_handler.go:68), defeating the per-`request_id` unique-index path. Only `HasPendingForRecipient` survives.
  - **(b) "Query `wallet_payments WHERE advance_request_id = ? AND status NOT IN (terminal)`."** There is no `advance_request_id` column on `wallet_payments`. The link is `entity_id` (wallet_payment_service.go:188, `EntityID: in.EntityID`, set from `&p.AdvanceRequestID` at disbursement_execute_worker.go:106). The plan's proposed query will fail to compile/run.
- **Failure scenario:** The cook writes the dedup query exactly as the plan says (`WHERE advance_request_id = ?`), the migration/query fails at runtime, and the test suite may not catch it if the test stub doesn't enforce column names (it usually doesn't). Or the cook "fixes" it to `entity_id` and discovers the dedup is now a strict superset of the existing `HasPendingForRecipient` guard — meaning the 409 fires for cases that currently succeed (e.g. a legitimately stuck `authorised` row that ops wants to override via retry). The plan's risk note acknowledges "stuck non-terminal row blocks legit retries" but does not say how to distinguish "stuck" from "intentionally in-flight".
- **Evidence:**
  - Column name: `wallet_payment_service.go:188` (`EntityID: in.EntityID`); `tx_wallet_payment_repository.go:38-43` (Create persists `*domaintx.WalletPayment`, no field tag for `advance_request_id`); the unique constraint name in `isDuplicateRequestIDError` (wallet_payment_service.go:244-246) is `idx_wp_request_id` — keyed on `request_id`, not `advance_request_id`.
  - Existing downstream dedup: `wallet_payment_service.go:163-169` (`HasPendingForRecipient`); `disbursement_execute_worker.go:108-122` (terminal-skip on retry).
  - Fresh `RequestID` per retry: `retry_disbursement_handler.go:68`.
- **Suggested fix:** Rewrite H6 as: "Pre-flight dedup query keyed on `entity_id = advanceRequestID AND status NOT IN (terminal)` — note the column is `entity_id`, not `advance_request_id`. This is a STRICTER check than the existing `HasPendingForRecipient` recipient-keyed guard (`wallet_payment_service.go:163`); document that the 409 path is intended for cases where the EXISTING downstream guard would still let a second transfer through (i.e. recipient changed banks between retries, or the prior row is terminal but the IPN/recon hasn't caught up). Return 409 ONLY for non-terminal `entity_id` matches; do not block when the only non-terminal row belongs to a different `entity_id`." Also: bind the `RequestID` to `(advance_request_id, amount)` as the plan already says — but note that this still doesn't make the per-`request_id` unique index catch retries, because the retry path regenerates `RequestID`. The real fix is to either (i) reuse the prior `RequestID` on retry, or (ii) add a unique partial index on `(entity_id)` filtered to non-terminal statuses — the plan should pick one.

## Finding 3: H7's `MarkReconciled` precondition ignores that `ReconcilePayment` already enforces a status allowlist upstream, and the plan omits the actual allowlist
- **Severity:** Medium
- **Location:** Phase 1, section "Architecture" (H7 bullet); phase-01 lines 21, 37
- **Flaw:** The plan says "add `WHERE id = ? AND status IN (...)`" but defers the actual allowlist to "enumerate with the reconcile-service owner." The codebase already has the answer: `ReconcilePayment` (wallet_payment_service.go:711-780) only calls `MarkReconciled` from `case StateFailed`, `case StateCompleted`, `case StateAuthorised, StateVerified` — `StatePending` and `StateReversed` fall through to the default "skipped" branch. So the legal prior states are exactly `{failed, completed, authorised, verified}`. The plan sends the cook on a wild goose chase to "coordinate with the owner" when the answer is in the same file as the bug.
- **Failure scenario:** The cook ships an over-narrow allowlist (e.g. only `{failed, authorised}`) because the plan didn't tell them `completed` and `verified` are also legal recon sources, and the daily midnight cron (`ReconcilePayment`) starts returning "unexpected status" errors for legitimately completed rows that need their `reconciled_at` stamp set. Production money-flow monitoring breaks silently.
- **Evidence:** `wallet_payment_service.go:719-777` — the `switch row.Status` cases that call `MarkReconciled` are exactly `StateFailed` (720), `StateCompleted` (743), and `StateAuthorised, StateVerified` (753). `MarkReconciled` itself (`tx_wallet_payment_repository.go:273-292`) has no status precondition today, confirming the audit-cited gap.
- **Suggested fix:** Replace "enumerate allowed transitions with the reconcile-service owner" with: "Allowlist = `{StateFailed, StateCompleted, StateAuthorised, StateVerified}` — sourced from `ReconcilePayment`'s `switch row.Status` cases (wallet_payment_service.go:719-777). `StatePending` and `StateReversed` are intentionally excluded."

## Finding 4: M12 cites the wrong `ResolveFee` — there are two services with that method and different signatures, only one of which is the OnePay-path bug
- **Severity:** High
- **Location:** Phase 2, section "Related Code Files" (M12 line); phase-02 line 25
- **Flaw:** The plan says "Modify `backend/internal/app/services/.../fee_schedule_service.go` (M12 — `ResolveFee` 279-302)". There are TWO `fee_schedule_service.go` files:
  - `advance_payment/fee_schedule_service.go:237` — `ResolveFee(ctx, amount uint64, at time.Time) uint64`. Used by the FlexPay calculator. Returns 2%/10000 fallback on missing schedule (lines 240-243).
  - `disbursement/fee_schedule_service.go:279` — `ResolveFee(ctx, provider string, at time.Time) int64`. Used by the disbursement execute worker (the OnePay path). Returns `fallbackFeeForProvider(provider)` (lines 280-287), which is `200` for 9pay and **`0` for everything else (including OnePay)** — this is the silent-revenue-loss bug the audit cites.
  - The cited line range "279-302" matches the **disbursement** file, but the plan's path `app/services/.../fee_schedule_service.go` is ambiguous and a cook who opens the wrong file first (the `advance_payment` one) will modify the wrong service. Worse, `wallet_payment_service.go:135` calls `s.feeProvider.GetDisbursementFeeVND(ctx, providerName)` which routes to `disbursement.FeeScheduleService.ResolveFee` — the plan does not mention this indirection, so the cook may also "fix" `GetDisbursementFeeVND` and double-apply the change.
- **Failure scenario:** Cook modifies `advance_payment/fee_schedule_service.go` (changes return signature to `(fee, waived, err)`), breaking the FlexPay calculator's `FeeResolver` interface (calculator.go:12) and the build, then has to back out. Or: cook correctly modifies `disbursement/fee_schedule_service.go` but does not realize `wallet_payment_service.go:135` is the only caller via `GetDisbursementFeeVND`, and the new `err` return path is silently swallowed because `Initiate` (the caller) does not propagate it.
- **Evidence:**
  - Two files: `advance_payment/fee_schedule_service.go:237` and `disbursement/fee_schedule_service.go:279` — both have `ResolveFee`, different signatures.
  - Caller indirection: `wallet_payment_service.go:135` (`fee = s.feeProvider.GetDisbursementFeeVND(ctx, providerName)`) → `disbursement/fee_schedule_service.go:66-68` (`GetDisbursementFeeVND` wraps `ResolveFee`).
  - `Initiate` (the actual hot path) calls `GetDisbursementFeeVND` synchronously at wallet_payment_service.go:135 with no error return — changing `ResolveFee` to return `err` requires changing `GetDisbursementFeeVND`'s signature too, which the plan does not mention.
- **Suggested fix:** Pin the path explicitly: "`backend/internal/app/services/disbursement/fee_schedule_service.go:279` (NOT `advance_payment/fee_schedule_service.go:237` — that one is the FlexPay calculator path, distinct bug, do not touch)." Also: "Changing `ResolveFee` to `(fee, waived, err)` requires changing `GetDisbursementFeeVND` (line 66) to `(int64, bool, error)`, which requires changing `Initiate` (wallet_payment_service.go:135) to propagate the error and reject the disbursement. The error must surface as a non-retryable asynq failure (currently `Initiate` returns `(row, err)`; the worker at disbursement_execute_worker.go:108-114 already returns the error — confirm it does not fall into the `ErrDuplicatePaymentInProgress` branch)."

## Finding 5: H8 `email_verified` check placement creates a user-enumeration oracle; absent-claim failure mode unspecified
- **Severity:** Medium
- **Location:** Phase 3, section "Implementation Steps" step 1 (H8); phase-03 line 30
- **Flaw:** The plan says "In `LoginWithGoogle`, after the email is extracted (~line 494), read `payload.Claims["email_verified"]`; if not `true`, audit + return unauthorized." Two problems:
  - **(a) User enumeration.** Line 494 is AFTER the email is extracted but BEFORE the user lookup at line 497. If the cook places the check between 494 and 497 (the natural reading of "after the email is extracted"), an unverified token still leaks whether the user exists — because the next branch (line 497-507) returns a different error message (`MsgGoogleAccountNotLinkedVN`) than the unverified branch. The check must go BEFORE the user lookup, with the same generic error message and same audit pattern as the existing branches.
  - **(b) Absent-claim failure mode.** The plan says "if not `true`" but does not specify what happens when `email_verified` is **absent** from `payload.Claims`. Go's `map[string]any` lookup returns the zero value (`nil`), and `nil == true` is `false` — so the check "reject if not true" happens to do the right thing by accident. But the audit row should distinguish "claim present and false" from "claim absent" because the latter is a token-shape anomaly (potentially a forged or stale refresh token). The plan does not call this out.
- **Failure scenario:** Cook inserts the check at line 495 (after email extraction, before user lookup). Attacker submits an unverified-email token for `admin@tingting.vip`; the response differs based on whether that email is registered, enabling silent account enumeration before the actual takeover.
- **Evidence:** `auth_service.go:484-507` — the email extraction (484-494) precedes the user lookup (497-507); the user-lookup branches return distinct error codes/messages (`MsgGoogleAccountNotLinkedVN` at 501, 506).
- **Suggested fix:** Specify: "Insert the `email_verified` check IMMEDIATELY AFTER `idtoken.Validate` succeeds (after line 482, BEFORE email extraction at 484). Use the same generic `MsgInvalidCredentialsVN` error and the same audit-row shape as the existing failed-validation branches. Treat claim-absent and claim-`false` identically in the reject path but log a distinct audit reason ('email_verified missing' vs 'email_verified false') so token-shape anomalies surface."

## Finding 6: H10's "ownership check" integration point is unspecified; the existing handler has no actor/subject binding
- **Severity:** Medium
- **Location:** Phase 3, section "Implementation Steps" step 4 (H10); phase-03 line 33
- **Flaw:** The plan says "Wire `CanUserModifyUser(actor, target)` into the user PUT handler" but (a) does not name the handler (`UserHandler.UpdateUser` at `user.go:92-110`), and (b) the handler today has no concept of "actor scope" — it parses `id` from the path and calls `userService.UpdateUser(ctx, id, req)` with no project/tenant context. The plan does not say where the actor's project scope comes from (JWT claim? session? a separate `adv_partner_projects` table?). Without that, `CanUserModifyUser` cannot be implemented.
- **Failure scenario:** Cook implements `CanUserModifyUser` but has no source for `actor.ProjectScope`, guesses wrong (e.g. reads from a query param the frontend doesn't send), and the check is always-allow or always-deny. Combined with the line-119 deletion, this either re-opens the IDOR or breaks all adv_partner user edits.
- **Evidence:** `user.go:92-110` — `UpdateUser` reads only `id` from path + `req` from body; no `c.Get("user_id")` / `c.Get("role")` / project-scope extraction. Casbin middleware (`casbin_policy.csv:119`) is the only thing currently gating the route; there is no ownership data model in the handler path.
- **Suggested fix:** Specify the integration precisely: "Modify `UserHandler.UpdateUser` (`user.go:92-110`). Read actor from JWT via the existing `c.Get('user_id')` / `c.Get('role')` pattern (verify the actual claim names against `middleware/auth.go` before coding). For `adv_partner` role, the actor's project scope is sourced from `<X>` (the plan must identify the table/column — likely the same join that backs `/api/v1/adv-partner/users/*`). Reject with 403 if `target.role == admin` OR `target` is not in actor's project scope."

## Finding 8: Cross-phase "disjoint files" claim is true for ownership but false for shared call-path risk between Phase 1 (H5) and Phase 2 (M12)
- **Severity:** Low
- **Location:** plan.md line 61 ("All four phases touch disjoint files ... can be implemented in parallel")
- **Flaw:** The claim is technically correct at the file level, but H5 and M12 both modify code that executes on the same logical path (advance-payment disbursement → wallet_payment → ledger). H5 adds `*gorm.DB` to `FlexPaySettlementService` and changes its constructor; M12 changes `ResolveFee` → `(fee, waived, err)` which changes `GetDisbursementFeeVND` → `(int64, bool, error)` which changes `WalletPaymentService.Initiate`'s error surface. If both phases land in parallel branches and merge without coordination, the `bootstrap/services/init.go` wiring (which constructs both services) will have conflicting constructor-call edits, and the `Initiate` error-surface change (M12) may mask the per-iteration tx error propagation H5 just added — because both touch error-return paths in money-flow code.
- **Failure scenario:** Two cooks work H5 and M12 in parallel. Both pass their own tests. Merge produces a `bootstrap/services/init.go` that compiles only because one cook's constructor change happens to align with the other's, but the integration test for the combined flow (settlement upload → fee stamp → ledger entry) was never run because each phase's tests assumed the other's signature was unchanged.
- **Evidence:** `bootstrap/services/init.go:318` constructs `FlexPaySettlementService` (H5 touches); same file constructs the disbursement `FeeScheduleService` and wires it into `WalletPaymentService` (M12 touches). Both edits land in the same file.
- **Suggested fix:** Add to plan.md Dependencies: "Phase 1 (H5) and Phase 2 (M12) both edit `bootstrap/services/init.go` constructor calls and both change error-return surfaces in money-flow code. Sequence them: H5 lands first (schema + tx wrapping), M12 lands second (fee signature change). Do NOT parallel-merge these two without running the combined settlement-upload → disbursement integration test post-merge."

## Summary

8 findings. The plan's structural shape is sound and the audit findings it cites are real (verified: H5's swallow-and-continue, H6's missing pre-flight dedup, H7's bare `WHERE id = ?`, H8's missing `email_verified`, M12's `fallbackFeeForProvider` returning `0` for OnePay, M1's live route). But the plan repeatedly confuses adjacent abstractions: two `ResolveFee` methods (Finding 4), two settlement services with different table semantics (Finding 1), a column named `entity_id` not `advance_request_id` (Finding 2), and an allowlist that already exists in the same file as the bug (Finding 3). A cook following this plan literally will introduce regressions on Phases 1 and 2 unless these are fixed before kickoff.
