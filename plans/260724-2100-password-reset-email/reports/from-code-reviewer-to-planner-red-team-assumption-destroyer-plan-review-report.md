## Finding 1: `GetByEmail` returns a NotFound *error* (not nil user) — plan's anti-enumeration path is correct, BUT the plan asserts this without the type guard the contract requires
- **Severity:** Medium (the assumption is true today; the *defense* is fragile)
- **Location:** Phase 2, section "Risk Assessment → GetByEmail semantics" (line 203) and Implementation step 2 (line 148)
- **Flaw:** The plan states "`GetByEmail` returns an error (not nil user) when not found — confirmed by reading `internal/domain/user.go` interface + existing usage in `crud.go`." The interface (`user.go:68`) only says `GetByEmail(...) (*User, error)` — it does NOT codify the not-found contract. The implementation today (`user_repository.go:107-113`) returns `domain.NewNotFoundError("user not found")`. But the plan's `RequestReset` does `if err != nil → return nil (no email)`. **Any** error from `GetByEmail` — including a transient DB error (`domain.NewInternalError` at line 112) — will be silently swallowed and produce a "check your email" 200.
- **Failure scenario:** Redis/MySQL blip during the lookup → `GetByEmail` returns `InternalError` → the request silently returns generic success → a real user with a real email never receives a reset link and is told to "check their inbox." No log, no metric, no retry. Support cannot diagnose. Worse: this is the *intended* anti-enumeration path being abused as a generic error sink.
- **Evidence:** `internal/infra/persistence/user_repository.go:107-113` returns two distinct error kinds; `internal/domain/user.go:68` interface carries no not-found contract. Phase 2 step 2 line 148: "If `err != nil` (not found) → return nil".
- **Suggested fix:** Distinguish the error kinds explicitly: `if errors.Is(err, domain.ErrNotFound) { return nil }` else log+propagate as internal error (still 200 to client, but logged at error level with the email redacted). Do not collapse all errors into the not-found branch.

## Finding 2: `ValidateToken` (where `TokensInvalidBefore` is enforced) is NOT called on `OptionalAuth` failures and NOT the middleware's own logic — plan mischaracterizes enforcement
- **Severity:** High
- **Location:** Phase 2, section "Architecture → design choices" (plan.md line 85) and "Risk Assessment → Session invalidation scope" (line 204); phase-02 line 204: "the auth middleware already enforces (reads `user.TokensInvalidBefore`)".
- **Flaw:** The check lives inside `AuthService.ValidateToken` (`auth_service.go:411-413`), which is invoked by `middleware/auth.go:42` for `Authenticate()` and `auth.go:79` for `OptionalAuth()`. The middleware itself does NOT read `user.TokensInvalidBefore`. The plan's prose ("the auth middleware already enforces") is technically true *only because* middleware delegates to `ValidateToken`. The acceptance criterion "all previously-issued JWTs for that user are invalid (they must log in again)" holds — but only because every protected route goes through this. **However**, the plan does not acknowledge that this enforcement requires an extra DB `GetByID` per request (line 411), so the post-reset login storm has a query cost the plan never flags.
- **Failure scenario:** A future change moves `TokensInvalidBefore` checking out of `ValidateToken` (e.g. into a faster JWT-claim-only path for performance) → password-reset session-kill silently stops working, and nothing in this feature's tests would catch it (the integration test in Phase 3 only checks login-with-old-password fails once, immediately, before any refactor). The plan's wording ("already enforced") encourages future readers to assume it is permanent middleware behavior.
- **Evidence:** `internal/app/services/auth/auth_service.go:411-413`; `internal/transport/http/middleware/auth.go:42,79`; `internal/app/services/auth/auth_service.go:379` (`func (s *AuthService) ValidateToken`). Phase-02 line 204 + plan.md line 85.
- **Suggested fix:** Restate as "session kill relies on `AuthService.ValidateToken` checking `user.TokensInvalidBefore` on every authenticated request; the reset flow merely sets the timestamp. Add an integration test that asserts the kill persists across a server restart and is NOT cached in middleware."

## Finding 3: `cfg.OTP.Enabled` (default **false**) gating is conflated with reset-email delivery — dev inboxes will never receive a reset link
- **Severity:** Critical
- **Location:** Phase 2, Implementation step 6 (line 183): "use `email.NewResendProvider(cfg.Notification.ResendAPIKey)` if production, same gating logic as OTP, so reset emails reach real inboxes even in dev sandbox mode".
- **Flaw:** The plan says to mirror OTP's sender-selection logic. That logic is at `services/init.go:608-611`: `otpEmailSender := emailProvider; if cfg.OTP.Enabled { otpEmailSender = email.NewResendProvider(...) }`. The default for `OTP_ENABLE` is **`false`** (`config.go:421`). So in default dev config, OTP *and* (per the plan's instruction) reset-email delivery both use the `SandboxProvider` (the `else` branch at `init.go:163-167`). The Phase 3 integration test step 3 explicitly relies on intercepting the token via `SandboxProvider.LastSent()`. **The two phases contradict each other.**
- **Failure scenario:** Implementer follows Phase 2 step 6 → reset emails go to Sandbox in dev. Implementer then implements Phase 3 step 4 (sandbox capture accessor) and step 5 (read token from sandbox). That is internally consistent. But the *acceptance criterion* "user receives a branded email within ~30 seconds" (plan.md line 135) is unverifiable in default dev. Worse: if someone sets `OTP_ENABLE=true` to test login in dev (a common action), then reset emails go to Resend — but the Phase 3 test will fail because `SandboxProvider.LastSent()` returns nil (no capture). The plan never resolves this fork.
- **Evidence:** `internal/app/bootstrap/services/init.go:608-611` (OTP sender gate), `init.go:163-167` (env-based provider select), `internal/config/config.go:421` (`OTP_ENABLE=false` default), `internal/config/config.go:588` (Resend key required only when `OTP_ENABLE=true`). Phase-02 line 183 vs phase-03 line 33.
- **Suggested fix:** Decide explicitly. Either (a) reset-email sender = SandboxProvider in non-prod (consistent with `emailProvider`), and the integration test reads from sandbox unconditionally — and drop the "same gating as OTP" instruction; or (b) reset emails use Resend whenever `PASSWORD_RESET_ENABLE=true`, in which case the integration test cannot rely on `SandboxProvider.LastSent()` and needs a different token-retrieval mechanism (e.g. a test-only env hook in the service). State the decision in the plan; do not let implementers guess.

## Finding 5: `passwordResetEmailKeyGetter` must replicate the body-read-then-restore trick exactly — the plan defers the load-bearing detail to a comment
- **Severity:** High
- **Location:** Phase 2, section "Rate limiter" (line 121-124): "// Read body (capped at 4 KiB), restore it, extract JSON "email". Mirror loginAccountKeyGetter exactly. Fall back to "ip:" + c.ClientIP()."
- **Flaw:** The plan leaves the body-restore as a one-line pseudocode comment. This is the *only* mechanism preventing the downstream `helpers.BindJSON` from receiving an empty body and 400-ing every request. The reference `loginAccountKeyGetter` (`rate_limit.go:123-156`) is 33 lines of non-obvious code: `io.ReadAll(io.LimitReader(...))`, then `c.Request.Body = io.NopCloser(bytes.NewReader(raw))`. If the implementer forgets the restore (a very easy mistake — gin's body is a one-shot reader), every password-reset request fails at `helpers.BindJSON` (`helpers/request.go:22`) with EOF → `BindJSON` returns false → handler returns early → the anti-enumeration 200 is never sent → the rate-limit count is also consumed but no email is ever generated.
- **Failure scenario:** Implementer writes `passwordResetEmailKeyGetter` that reads the body for the email key but does NOT restore it. `make dev` smoke test in Phase 2 step 8 returns 200 (because `BindJSON` failure causes early `return` *before* `response.Success` — actually no: `helpers.BindJSON` itself calls `response.BadRequest` and the handler returns immediately with 400). So the plan's step 8 success criterion "Manual curl returns 200" silently fails, but the implementer may misdiagnose it as a routing issue.
- **Evidence:** `internal/transport/http/middleware/rate_limit.go:123-156` (loginAccountKeyGetter, the only correct pattern); `internal/transport/http/helpers/request.go:22` (`BindJSON` reads body once). Phase-02 line 121-124.
- **Suggested fix:** Inline the full getter implementation in the plan, not a "// mirror exactly" comment. Specifically: read with `io.LimitReader(c.Request.Body, 4<<10)`, capture into `raw`, immediately reassign `c.Request.Body = io.NopCloser(bytes.NewReader(raw))`, THEN unmarshal. Add a unit test on the getter asserting the body is re-readable.

## Finding 6: `NewAuthHandler` is wired with an extra dependency, but the AuthHandler struct lives in `handlers/auth.go` which does not import `passwordreset` — a cross-package cycle risk the plan ignores
- **Severity:** Medium
- **Location:** Phase 2, Implementation step 4 (line 177): "Update the single call site in `container.go`". Phase 1 listed the service path as `backend/internal/app/services/passwordreset/service.go`.
- **Flaw:** Adding `passwordResetService *passwordreset.Service` to `AuthHandler` (in `internal/transport/http/handlers/auth.go`) requires importing `api-server/internal/app/services/passwordreset` from the `handlers` package. The handlers package today imports `app/services/auth` and `app/services/user` (see `auth.go:7-8`). This works only if `passwordreset` does not, in turn, import `handlers`. The plan never states this constraint. More importantly: the plan's "narrow port" design (Phase 2 line 47-52) is the correct way to avoid coupling — but the *handler* still imports the concrete `*passwordreset.Service`, defeating the decoupling the narrow ports were designed to provide.
- **Failure scenario:** Implementer, following the narrow-port pattern in the service, then adds a concrete `*passwordreset.Service` field to the handler. If a later refactor has `passwordreset.Service` call back into a handler (e.g. for URL generation), Go refuses to compile with an import cycle, and the narrow ports buy nothing.
- **Evidence:** `internal/transport/http/handlers/auth.go:7-8,21` (imports + constructor); plan phase-01/02 service path `backend/internal/app/services/passwordreset/`. Plan phase-02 line 97: "`AuthHandler` gets a new `passwordResetService *passwordreset.Service` field + constructor param".
- **Suggested fix:** Either (a) keep the handler importing the concrete service (simplest; document that `passwordreset` must never import `handlers`), or (b) define the handler's dependency as an interface (`RequestReset`, `ConfirmReset` methods) in the `handlers` package or a shared `ports` package, consistent with the narrow-port philosophy the plan already introduces for `UserService`.

## Finding 8: Anti-enumeration contract is broken by *response timing* — the plan acknowledges timing as a risk but ships no mitigation
- **Severity:** High
- **Location:** Phase 2, Implementation step 2 (lines 147-152): unknown-email path returns nil immediately (no Redis write, no goroutine, no email send); known-email path does Redis `SET`, spawns a goroutine, etc. Phase 4 Risk Assessment (line 99) admits the concern then dismisses it: "backend always returns 200... the client only ever sees 200 or network-error."
- **Flaw:** The client sees 200 in both cases, but the *server-side latency* differs by orders of magnitude. Unknown email: ~1 DB round-trip (~1-5ms). Known email: DB lookup + Redis `SET` + goroutine spawn (~5-50ms, plus the goroutine competes for scheduler). A timing side-channel distinguishes "email exists" from "email doesn't" with high accuracy after a few samples. The plan's own risk table (plan.md line 160) rates this "Medium" with mitigation "no timing differential (email send is async)" — but the *token creation* (Redis SET) is synchronous and happens before the goroutine, so it IS in the request path.
- **Failure scenario:** Attacker submits 100 emails, measures response latency, clusters into two groups, identifies valid emails with >90% accuracy. Enumerates the user base. Combined with no per-IP rate limit (the limiter is per-email, so an attacker probing many distinct emails is uncapped), this is a real enumeration vector.
- **Evidence:** Phase-02 line 147-152 (RequestReset path); `internal/infra/persistence/user_repository.go:107` (DB lookup on every request); rate limiter is per-email (phase-02 line 116-119), so distinct-email probes are unlimited per IP.
- **Suggested fix:** Either (a) perform the Redis `SET` and goroutine spawn in *both* paths (for unknown emails, write a decoy key, spawn a no-op goroutine) so latency is constant, or (b) add a per-IP rate limit *in addition to* the per-email limit (e.g. 30/hour/IP) to cap probing volume, or (c) add a constant minimum response delay (e.g. `time.Sleep(randomJitter)`). Pick one and state it.

## Finding 9: `SandboxProvider.LastSent()` does not exist — the method is `LastEmail()`, returning `*CapturedEmail` (not `*domain.EmailMessage`)
- **Severity:** High (test-blocking)
- **Location:** Phase 3, Implementation step 4 (lines 70-76): proposes adding `func (p *SandboxProvider) LastSent() *domain.EmailMessage`.
- **Flaw:** The accessor **already exists** with a different name and different return type: `SandboxProvider.LastEmail() *CapturedEmail` (`sandbox_provider.go:81`). `CapturedEmail` is a distinct struct (with its own fields, defined near line 170 in `email.go`). The plan's proposed `LastSent()` returns `*domain.EmailMessage`, which is the *input* type, not the captured type. An implementer following the plan literally will either (a) add a duplicate accessor that shadows/confuses the existing one, or (b) waste time discovering the existing one. Worse, Phase 3 step 4 says "if it doesn't already expose the last-sent message... add" — implying the author did not verify, despite the plan's claim (phase-03 line 33) "Confirm by reading `sandbox_provider.go`."
- **Failure scenario:** Implementer adds `LastSent()` returning `*domain.EmailMessage`. But the SandboxProvider stores `*CapturedEmail` (different struct). To return `*domain.EmailMessage`, they must add a conversion or store a second copy. Either way, the integration test's token extraction (`SandboxProvider.LastSent().HTMLBody` or similar) will not match the actual captured shape, and parsing the token out of the HTML requires regex against the magic-link URL — which the plan never specifies.
- **Evidence:** `internal/infra/email/sandbox_provider.go:81` (`LastEmail() *CapturedEmail`), `:72` (`SentEmails() []*CapturedEmail`); `internal/domain/email.go:170` (`CapturedEmail` struct with `Metadata map[string]string`). Phase-03 line 70-76.
- **Suggested fix:** Replace Phase 3 step 4 entirely: "Use the existing `SandboxProvider.LastEmail() *CapturedEmail` accessor. The captured email's HTML body contains the magic link; extract the token via a regex against `resetURL + "?token=" + (.+?)"`. Document the regex in the test."

## Finding 10: `users.tokens_invalid_before` exists, but the plan's "no migration needed" claim is true *only* because it ignores the `EmailKind`/observability gap (Finding 7) and the missing `password-strength` route (Finding 4) — both of which imply schema/route work the plan omits
- **Severity:** Medium
- **Location:** Phase 6, section "Database" (line 24-29): "No migration needed."
- **Flaw:** The column-existence claim is correct: migration `086_add_user_tokens_invalid_before.up.sql` adds it. But the plan's overall "self-contained, no migration" framing masks two adjacent gaps that DO require work the plan under-specifies: (a) if Finding 7's fix is adopted (new `EmailKindPasswordReset`), that is a code constant, fine — but if the team wants DB-backed email logging (the codebase has `repos.Notification` for notifications), reset emails are NOT logged to the DB, unlike OTP-equivalent audit trails; (b) the plan never reconciles that OTP codes are audited via `OTPPendingStore` + login events, but reset tokens have no audit record at all (no "reset requested" event, no "reset consumed" event beyond `PasswordChangedEvent`). For a security-sensitive flow, the absence of an audit trail is a gap.
- **Failure scenario:** Security incident: an attacker requests resets for many users. There is no DB record of which emails were targeted, only Redis keys (TTL'd, gone in 30min) and possibly Resend logs (external). Incident response cannot reconstruct the attack from the application DB.
- **Evidence:** `migrations/086_add_user_tokens_invalid_before.up.sql:9` (column exists); `internal/infra/cache/otp_pending_store.go:72` (OTP has a Redis store AND the login flow publishes `UserLoginEvent`); Phase 2 publishes only `PasswordChangedEvent` (phase-02 line 162) — no `PasswordResetRequestedEvent`.
- **Suggested fix:** Either accept the audit gap and document it as a deliberate tradeoff, or add a lightweight `PasswordResetRequestedEvent` (best-effort publish) so the request side is auditable. State this decision in Phase 6.
