## Finding 1: `html.partner-route-active` does NOT mirror admin's actual portal-reaching selector; the `[data-partner-ui]` half of the proposed scope cannot be set because the plan never adds that attribute
- **Severity:** Critical
- **v1 resolution check:** PARTIALLY RESOLVED (v1 finding #6 claimed resolved by "mirror AdminLayout's `html.admin-route-active` classList" — but the plan copies only half the mechanism)
- **Location:** Phase 1, section "Architecture" (lines 38-49); Phase 4 Step 4 ("Portal scope verification")
- **Flaw:** Phase 1's CSS template shows `html.partner-route-active [data-partner-ui]` and `html.partner-route-active [data-radix-popper-content-wrapper]` as the two scopes. The plan's narrative (plan.md Key Decision #3, line 145) claims this "mirrors AdminLayout.tsx:101-102 exactly." It does not. AdminLayout (`/Users/dev/Documents/projects/payroll/frontend/src/layouts/AdminLayout.tsx:108-112`) sets THREE things on the wrapper div: `data-admin-ui`, `data-theme="congtruang"`, AND `className="admin-shell-scope"`. The admin CSS that reaches portals actually lives at `/Users/dev/Documents/projects/payroll/frontend/src/styles/admin-daisy.css:35` as `[data-admin-ui] [data-radix-popper-content-wrapper]` — note it is **attribute-scoped on the wrapper div**, NOT on the `html` class. The `html.admin-route-active` selectors in admin-daisy.css:393-409 only style `[role="dialog"]` / `[role="menu"]` chrome (border/bg), they do NOT establish the wrapper scope that elevates z-index over the sidebar. The v2 plan adds the classList effect but the "Modify PartnerLayout.tsx" touchpoint (plan.md:190) only lists "add the classList effect" — there is no instruction to add `data-partner-ui` to the wrapper div. Without that attribute, the proposed `html.partner-route-active [data-partner-ui]` selector in Phase 1 Architecture matches nothing, and Phase 4 Step 4's instruction "the Radix portal content should be reachable by partner CSS rules via the `html.partner-route-active` scope" cannot be satisfied because no `[data-partner-ui]` element will exist.
- **Failure scenario:** Implementer follows the plan verbatim: adds the classList effect and writes `html.partner-route-active [data-radix-popper-content-wrapper] { ... }` rules in partner.css. A partner Sheet/Dialog (Radix portal) opens. The z-index / stacking-context rules in `PartnerLayout.tsx:24` (`overflow-hidden` on the content div) and partner.css are never applied because (a) `[data-partner-ui]` is never set on any DOM node, and (b) the `html.partner-route-active [data-radix-popper-content-wrapper]` selector the plan template shows has no `!important` z-index override like admin's. Partner sheets render behind the sidebar / get clipped, exactly the bug v1 was rejected for — re-introduced by an incomplete mirror.
- **Evidence:** `/Users/dev/Documents/projects/payroll/frontend/src/layouts/AdminLayout.tsx:108-112` (three-part wrapper scope); `/Users/dev/Documents/projects/payroll/frontend/src/styles/admin-daisy.css:35` (`[data-admin-ui] [data-radix-popper-content-wrapper] { z-index: 80 !important; }`); `/Users/dev/Documents/projects/payroll/frontend/src/layouts/PartnerLayout.tsx:20-37` (no `data-*` attribute anywhere); plan.md:190 (Modify list omits wrapper-attribute addition); phase-01-foundation.md:46-48 (selector template references an attribute no element will carry).
- **Suggested fix:** Either (a) drop the `[data-partner-ui]` selector half entirely from Phase 1 and rely solely on `html.partner-route-active [role="dialog"|"menu"|"listbox"]` (matching admin-daisy.css:393-409), with explicit Phase 4 assertion that `[data-partner-ui]` is intentionally unused; or (b) add `data-partner-ui=""` to the wrapper div in PartnerLayout.tsx:21 as a required Phase 1 step and cite AdminLayout.tsx:109 as the precedent.

## Finding 2: classList effect with `[]` deps does NOT mirror admin's `[isAdmin]` guard — a role-less partner effect will set the class even when `ProtectedRoute` has redirected away on token expiry
- **Severity:** High
- **NEW v2 finding**
- **Location:** Phase 1, section "Architecture" (lines 30-36) and Implementation Step 2 ("Use `[]` deps")
- **Flaw:** AdminLayout.tsx:99-103 guards the classList mutation behind `if (!isAdmin) return;` with `[isAdmin]` deps — the class is only added when the role check actually passes inside the component. The partner plan hard-codes `useEffect(() => { classList.add(...); return () => classList.remove(...); }, [])` with empty deps and no `useAuth`/role guard. PartnerLayout.tsx:40-49 wraps children in `ProtectedRoute requiredRole="partner"`, but `ProtectedRoute` (ProtectedRoute.tsx:18-65) has an async redirect: on mount it `setTimeout(100ms)` then `navigate('/login?redirect=...')`. During that 100ms window, `PartnerLayoutInner` mounts, runs the empty-deps effect, and stamps `partner-route-active` on `<html>`. The cleanup only fires on unmount, which happens after the redirect. Result: a brief but real interval where the page is on `/login` (or being torn down to it) with `partner-route-active` still on the document element.
- **Failure scenario:** An attacker with an expired partner session hits `/partner/dashboard` directly. The class is applied for ~100ms before the redirect; if any partner.css rule (Phase 3 will populate them) sets base typography, autofill colors, or selection styles under `html.partner-route-active`, those leak onto the `/login` render briefly. More importantly, after a real logout-then-login-as-admin flow within the same SPA session, a stale class could persist if React 18 StrictMode double-mount races with the redirect timer — the plan's Step 6 check only validates "class still present after remount" on `/partner/*`, never validates "class absent during the redirect window."
- **Evidence:** `/Users/dev/Documents/projects/payroll/frontend/src/layouts/AdminLayout.tsx:99-103` (guards on `isAdmin`); `/Users/dev/Documents/projects/payroll/frontend/src/components/ProtectedRoute.tsx:31-43` (100ms setTimeout redirect); `/Users/dev/Documents/projects/payroll/frontend/src/layouts/PartnerLayout.tsx:40-49` (no useAuth call); phase-01-foundation.md:30-36 (`[]` deps, no role gate).
- **Suggested fix:** Mirror admin exactly: read `const { user } = useAuth()` in `PartnerLayout`, derive `const isPartner = user?.role === 'partner'`, gate the effect with `if (!isPartner) return;` and `[isPartner]` deps. Update Phase 1 Step 2's "Use `[]` deps" instruction to "Use `[isPartner]` deps, mirroring AdminLayout.tsx:99-103."

## Finding 3: Cross-surface consumer check for `components/shared/*` edits has no circuit breaker — Phase 3 can proceed and regress admin/employee with only a Phase 4 *screenshot* (no fail gate)
- **Severity:** High
- **NEW v2 finding**
- **Location:** Phase 3 Risk Assessment ("A `components/shared/*` edit during polish regresses an admin or employee consumer") and Phase 4 Step 9
- **Flaw:** The plan correctly identifies the risk (plan.md:182 Risk Controls) and Phase 2 Step 6 maps the blast radius. But Phase 3 only says a shared-primitive edit "is additive (new optional prop)" or "partner is the sole consumer." There is no Phase 3 *block* if a non-additive edit is required — the only enforcement is "Phase 4 runs the cross-surface screenshot check." Screenshots are visual QA, not an automated gate; a Pixelmatch/diff threshold is not specified, and Phase 4 Step 9 is worded as "Confirm no visual regression" with no defined failure action beyond "requires a Phase 2 audit update." An attacker-minded reviewer notes: `MobileBottomNav.tsx` is shared across admin, adv_partner, and partner branches (MobileBottomNav.tsx:1-14 imports); `BankTransferHistoryPageContent` is shared admin+partner with a `variant` prop (BankTransferHistoryPageContent.tsx:280-284). A Phase 3 "visual token tweak" to either file changes the partner branch and silently drifts admin's branch unless the screenshot diff catches it.
- **Failure scenario:** Phase 3 polish decides the partner `MobileBottomNav` active indicator color should change. Implementer edits MobileBottomNav.tsx without isolating the change to the partner branch (no role check in the file). Phase 4 Step 9 screenshot is captured but the reviewer eyeballs "looks fine" because the diff is subtle. Admin/adv_partner active indicator is now wrong in production. No automated regression gate exists.
- **Evidence:** `/Users/dev/Documents/projects/payroll/frontend/src/components/MobileBottomNav.tsx:1-14` (shared file, no per-role wrapper); phase-03-foundation.md Risk Assessment (mitigation = "Phase 4 runs the cross-surface screenshot check"); phase-04-verification.md Step 9 ("Confirm no visual regression" — no threshold, no automated fail gate).
- **Suggested fix:** Add a Phase 3 hard rule: any edit to `components/shared/*`, `components/MobileBottomNav.tsx`, or `components/payroll/*` must be either (a) additive (new optional prop with default preserving current behavior), or (b) gated behind an explicit role/surface check inside the file. Non-conforming edits block Phase 3 completion. Phase 4 Step 9 should specify a pixel-diff threshold (e.g., <0.5% diff) and a fail action ("revert the shared edit and re-scope to partner-only wrapper").

## Finding 4: Optional mobile Payment History wiring (Phase 3 Step 8) silently widens the data path — partner mobile uses `useInfinitePaymentHistories` + `exportPaymentHistories`, which have NO client-side role filter, while the desktop partner view uses a different hook (`useBankTransferHistories`)
- **Severity:** High
- **NEW v2 finding**
- **Location:** Phase 3, Step 8 ("Optional: wire mobile Payment History")
- **Flaw:** The plan frames the App.tsx:282 route swap as a pure presentation change ("`BankTransferHistoryPageContent` is byte-unchanged"). What it ignores: the existing mobile file at `/Users/dev/Documents/projects/payroll/frontend/src/pages/mobile/partner/TimesheetsPage/PaymentHistoryPage.tsx:11-14` does NOT use `BankTransferHistoryPageContent` at all — it calls `useInfinitePaymentHistories` and `useExportPaymentHistories` directly. These hit `payrollService.getPaymentHistories` (`/Users/dev/Documents/projects/payroll/frontend/src/services/api/payroll.service.ts:30`) and `exportPaymentHistories` (line 41), endpoints that the desktop partner view never calls (desktop uses `useBankTransferHistories` → `getBankTransferHistories` → a DIFFERENT endpoint at `payrollService.getBankTransferHistories` line 17). The two hooks return different shapes and likely hit different backend routes with different authorization scopes. Wiring the mobile file as the partner `/partner/timesheet/payment-history` mobile view therefore changes which backend endpoint a partner user hits on mobile vs desktop — an authz surface change, not a presentation change.
- **Failure scenario:** Backend `getPaymentHistories` endpoint has different (broader) authorization than `getBankTransferHistories` — for example, it returns all payment records the user can see rather than only bank-transfer records scoped to the partner's employees. A partner user on mobile now sees a different (potentially wider) dataset than the same partner user on desktop. The plan's Phase 4 Step 6 only checks visual identity between `/partner/.../payment-history` and `/admin/.../payment-history` (shared component), NOT between partner-mobile and partner-desktop.
- **Evidence:** `/Users/dev/Documents/projects/payroll/frontend/src/pages/mobile/partner/TimesheetsPage/PaymentHistoryPage.tsx:11-14,86-105` (mobile uses `useInfinitePaymentHistories` + `useExportPaymentHistories`); `/Users/dev/Documents/projects/payroll/frontend/src/services/api/payroll.service.ts:17,30,41` (three distinct service methods); `/Users/dev/Documents/projects/payroll/frontend/src/pages/partner/PaymentHistoryPage/index.tsx:1-4` (desktop uses `BankTransferHistoryPageContent` → `useBankTransferHistories`); phase-03 Step 8 claims "desktop re-export is unchanged so admin's view is preserved" — true for admin, false for partner-mobile-vs-partner-desktop parity.
- **Suggested fix:** Either (a) defer the mobile wiring (the plan's stated default — make it the firm decision, not "optional"), or (b) if wiring is in scope, add a Phase 4 step that diffs the partner-mobile vs partner-desktop *response payload* (not just screenshot) for the same partner user, and confirm backend authorization is identical for the two endpoints. Document which backend route each hook hits before wiring.

- **NEW v2 finding (resolves a v1-adjacent concern the prompt raised)**
- **Location:** Phase 2 Step 4 (per-file greps) vs Phase 3 Step 7 ("Dead-code deletion sweep") and its success criterion
- **Flaw:** Phase 2 Step 4 correctly mandates "Record results per file. A file is safe to delete only if all three greps return zero hits for its name." Phase 3 keeps it. Phase 4 Step 3 `find` reports the folder still exists → success criterion fails → reviewer pressure to "just delete it to satisfy the gate." Folders may legitimately remain if they hold a kept file. Phase 3 success criterion should mirror this.

## Finding 6: `partner.css` placed AFTER `admin-daisy.css` in cascade (Phase 1 Step 4) creates a CSS injection-by-PR surface — any future broad-selector rule in partner.css overrides admin defaults globally if the class ever leaks
- **Severity:** Medium
- **NEW v2 finding**
- **Location:** Phase 1, Implementation Step 4 ("Place it after `@import './styles/admin-daisy.css';`")
- **Flaw:** The plan defends the cascade order with "surfaces are isolated — but cascade order is defensible." It is not defensible from a defense-in-depth angle. variables.css:313-314 shows admin tokens are scoped under BOTH `[data-admin-ui]` AND `html.admin-route-active` — meaning the admin token block matches whenever EITHER condition is true. If `partner-route-active` ever gets stuck on `<html>` (Finding 2 above shows a real path for this), and partner.css (loaded later) defines `html.partner-route-active { --primary: ... }`, that override wins over admin's `[data-admin-ui]` block due to source order — even on `/admin/*` routes. The plan's Risk Assessment (phase-01:92) only mitigates `:root` rules ("header comment forbids them"), not `html.partner-route-active` token overrides that the plan explicitly invites ("Add new `--partner-*` tokens under the `html.partner-route-active` block").
- **Failure scenario:** Phase 3 implementer adds `html.partner-route-active { --primary: 148 60% 58%; }` to partner.css (reasonable-looking token override). Finding 2's stale-class bug fires: `partner-route-active` is stuck on `<html>` after a partner→admin navigation race. Admin's primary color now renders with the partner accent on `/admin/dashboard` because partner.css loads after admin-daisy.css. Visual regression on admin is silent until a user reports it.
- **Evidence:** `/Users/dev/Documents/projects/payroll/frontend/src/styles/variables.css:313-314` (`[data-admin-ui], html.admin-route-active { --background: var(--admin-background); ... }` — admin tokens are gated by the SAME html class pattern); `/Users/dev/Documents/projects/payroll/frontend/src/index.css:1-5` (current cascade order: variables → base → utilities → premium → admin-daisy); phase-01 Step 4 (place partner.css after admin-daisy.css).
- **Suggested fix:** Either (a) load `partner.css` BEFORE `admin-daisy.css` so admin always wins when both classes are present (admin is the higher-trust surface), or (b) scope every partner token override under `html.partner-route-active:not([data-admin-ui])` so they cannot bleed into admin even on class leak. Phase 4 grep should assert no `html.partner-route-active {` rule exists without a `:not([data-admin-ui])` or descendant-selector guard.

## Finding 7: XSS / supply-chain surface from Tailkit MCP snippets is not addressed — Phase 3 translates "patterns" but the verification gate only catches literal color classes, not script/style/SVG injection vectors
- **Severity:** Medium
- **NEW v2 finding**
- **Location:** Phase 3 Step 5 ("Populate partner.css"), Phase 4 Step 2 (Tailkit literal-class grep), plan.md Key Decision #2
- **Flaw:** The plan says Tailkit snippets are "translated to project tokens" and Phase 4 Step 2 greps for `secondary-[0-9]|emerald-[0-9]|...|dark:` literal classes. That grep catches color-token drift but NOT: (a) inline `style={{ ... }}` with Tailkit-derived strings (e.g., `style={{ color: '#085f3e' }}`), (b) `dangerouslySetInnerHTML` if a snippet contains inline SVG/HTML, (c) hardcoded hex values like `#085f3e` / `#f8fafb` that bypass the token system entirely (note: PartnerLayout.tsx:27 ALREADY contains `rgba(8,120,62,0.07)` and `#f8fafb` literals, so the precedent for literal colors exists in partner code), (d) Tailkit snippets that ship `<script>` or `onload=` handlers if copied into a component body. The plan's grep regex is color-class-specific.
- **Failure scenario:** A Phase 3 polish copies a Tailkit empty-state snippet that includes an inline SVG with a `<script>` tag or an `onload` handler in a `<img>`. The literal-class grep passes (no `emerald-100` etc.), the build passes, the snippet renders user-influenceable HTML if any Tailkit example contained dynamic content. Lower probability than other findings but the plan claims "translate to project tokens, never copy-paste" with no enforcement beyond a color-class regex.
- **Evidence:** phase-04 Step 2 grep regex (color classes only); `/Users/dev/Documents/projects/payroll/frontend/src/layouts/PartnerLayout.tsx:27` (existing literal `rgba(...)` and `#f8fafb` colors — establishes precedent that partner code already has non-token colors, so the "translate to tokens" claim is aspirational); phase-03 Step 5 ("translate to project tokens" — no enforcement).
- **Suggested fix:** Extend Phase 4 Step 2's grep to also fail on: `dangerouslySetInnerHTML`, inline `style={{` containing hex/rgba literals in the touched files, and any `<script>` or `onload=`/`onerror=` in `.tsx`. Add a lint rule or grep gate: `grep -rnE "dangerouslySetInnerHTML|style=\{\{[^}]*#[0-9a-fA-F]{3,8}" frontend/src/pages/partner frontend/src/pages/mobile/partner frontend/src/styles/partner.css`.
