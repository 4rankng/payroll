**Plan:** Trend-aware cash-readiness forecast (detrend gamma + growth-adjusted P50)
**Reviewer role:** FAILURE MODE ANALYST — trace data flow, find where data gets lost, corrupted, double-counted, or mishandled

## Finding 1: `buildTimesheetCohort` returns chronologically UNSORTED series — OLS index-based fitting will fit noise, not trend

- **Severity:** Critical
- **Location:** Phase 2, section "Implementation Steps" step 4 + "Architecture" diagram; Phase 3, section "Architecture" (growthFactor)
- **Flaw:** Phase 2 introduces `olsFit` on indices `[0..n-1]` vs values, and Phase 3 computes `recentGrowthRates = [grandTotals[i]/grandTotals[i-1] for last 3 pairs]`. Both assume the `historical []cohortSeries` slice is ordered chronologically (index 0 = oldest month, index n-1 = newest). It is not. `buildTimesheetCohort` builds the series by iterating a Go `map[string]*acc` (`byMonth`), then appending to the `series` slice via `for forMonth, a := range byMonth`. Go map iteration order is randomized per run. The returned slice has no chronological guarantee.
- **Failure scenario:** On a given process run, the slice order may be `[Jun, Jan, Apr, Feb, May, Mar]`. OLS then fits a trend where index 0=Jun(457M), 1=Jan(80M), 2=Apr(158M)... producing a steeply NEGATIVE slope (the data appears to crash from 457M to 80M). The re-trended forecast `next_fitted = intercept + slope*n*phi` extrapolates downward, clamping to 0 (per step 5). The July forecast collapses to the gamma residual floor — the exact opposite of the plan's ≥300M acceptance criterion. On the next process restart, the map order changes and the forecast jumps to a different value, violating the "Deterministic output" constraint (plan.md line 158). The growth EWMA in Phase 3 likewise pairs wrong adjacent months (`grandTotals[i]/grandTotals[i-1]` where i-1 is NOT the prior calendar month).
- **Evidence:** `backend/internal/app/services/cash_readiness_forecast.go:255` (`byMonth := make(map[string]*acc)`), `:279` (`for forMonth, a := range byMonth` — map iteration, unsorted). Contrast with the wallet forecast which DOES preserve order: `backend/internal/app/services/wallet_demand_forecast.go:67-83` iterates an ordered `forMonths` slice. The existing gamma engine is order-INSENSITIVE (it fits on the multiset `rem` at `wallet_demand_forecast_math.go:427-443`), so the unsorted slice is latent today but becomes a hard bug the moment Phase 2 adds index-based OLS.
- **Suggested fix:** Before returning from `buildTimesheetCohort`, `sort.Slice(series, func(i,j int) bool { return series[i].forMonth < series[j].forMonth })`. Add a test asserting chronological order. This is a prerequisite for Phase 2, not a Phase 2 deliverable.

## Finding 2: Snapshot stores `proj.P50` (remaining accrual); accuracy logger compares it against `actual grand total` — units mismatch inflates error by the confirmed-payable floor

- **Severity:** Critical
- **Location:** Phase 1, section "Implementation Steps" step 3 + step 4
- **Flaw:** Step 3 says write "the P50/expected to Redis." The P50 the response exposes is `ProjectedP50` = `proj.P50` (line 181 of `cash_readiness_forecast.go`), which is the projected ADDITIONAL accrual from `cycleDayToday` through pay date — NOT the total cycle volume. Step 4 says "Reads the actual grand total via `GetAccrualCohort` + `buildTimesheetCohort`" and computes `absPctErr = |forecast - actual| / actual`. Comparing `proj.P50` (a remaining-window slice) against `grandTotal` (the full cycle) is a units mismatch.
- **Failure scenario:** July Ky-2: `confirmed` (already approved) = 120M, `proj.P50` = 180M (remaining). Snapshot stores 180M. Actual grand total at cycle end = 457M. Accuracy logger computes `|180 - 457| / 457 = 60.6%` and logs it — but the TRUE forecast error of the headline (`confirmed + proj.P50` = 300M vs 457M) is 34.4%. The logged accuracy is wrong by ~26pp, the rolling accuracy figure shown in the Phase 4 UI is bogus, and the ML-escalation trigger (">20% over 4 cycles") fires on phantom error. The existing backtest test (`cash_readiness_backtest_test.go:92`) correctly compares `observedSoFar + proj.P50` against `actualTotal` — the production logger omits the `observedSoFar` term.
- **Evidence:** `backend/internal/app/services/cash_readiness_forecast.go:181` (`ProjectedP50: proj.P50`) and `:152` (`confirmed := summary.PendingPaymentAmount`) — `proj.P50` is the remaining accrual only. Contrast: `backend/internal/app/services/cash_readiness_backtest_test.go:92` (`projected: observedSoFar + proj.P50`) — the test adds the observed-so-far floor; the plan's logger does not. Plan quote (phase-01 line 87): "Computes `absPctErr = |forecast - actual| / actual`" with `actual` = grand total (line 54).
- **Suggested fix:** The snapshot must store the full headline `cashToPrepare` (= `confirmed + proj.P50`, line 171) AND the `cycleDayToday` at snapshot time. The accuracy logger must reconstruct the "actual headline" = full cycle grand total, and compare headline-to-headline. Alternatively, store both `proj.P50` and `confirmed` and have the logger compare `confirmed + proj.P50` vs `grandTotal`. Either way, document the exact quantities being compared.

## Finding 3: Phase 2 architecture diagram fits OLS on `grandTotals[]`; Implementation Step 4 fits OLS on `rem[]` — two different series, two different trend slopes, contradictory plan

- **Severity:** High
- **Location:** Phase 2, "Architecture" diagram (lines 37-51) vs "Implementation Steps" step 4 (line 84-89)
- **Flaw:** The Architecture diagram says: `compute grandTotals[] from historical`, `olsFit(grandTotals) → (slope, intercept)`, `residuals[i] = grandTotals[i] - fitted[i]`. Implementation Step 4 says: "after computing `rem []float64` (remaining demand per historical cycle)... Fit OLS on the per-cycle remaining values (`rem`, not grand totals)". These are different series: `grandTotals` = full cycle totals (e.g., 80M, 130M, 457M); `rem` = the slice of the cycle between `fromCycleDay` and `throughCycleDay` (depends on today's position, changes every day). The trend ratio also differs: the diagram (line 38) says `trendRatio = max(grandTotals)/min`, but the actual code computes `trendRatio` on `rem` (`wallet_demand_forecast_math.go:458-461`).
- **Failure scenario:** An implementer following the Architecture diagram fits OLS on grandTotals and gets slope X. An implementer following Implementation Step 4 fits on `rem` and gets a different slope (because `rem` shrinks as `fromCycleDay` advances — early in the cycle `rem` ≈ grandTotal; late in the cycle `rem` ≈ a small tail). The detrended forecast is therefore cycle-day-dependent in a way the architecture never intended. Worse, `rem` can be near-zero late in the cycle (when `fromCycleDay` is close to `throughCycleDay`), making the OLS slope unstable and the gamma fit on residuals degenerate. The "≥300M" acceptance criterion becomes uncheckable because the result depends on which paragraph the implementer followed.
- **Evidence:** Plan phase-02 line 44 (`olsFit(grandTotals)`) vs line 85 ("Fit OLS on the per-cycle remaining values (`rem`, not grand totals)"). Code: `wallet_demand_forecast_math.go:426-443` computes `rem` from `cumulativeAt(throughCycleDay) - cumulativeAt(fromCycleDay)`, and `:458-461` computes `trendRatio` on `rem`, not grandTotals.
- **Suggested fix:** Pick ONE series. Given the engine already computes `trendRatio` on `rem` and that is what triggers the detrend branch, the detrend must also operate on `rem`. Delete the grandTotals-based architecture diagram or rewrite it to match. Reconcile the trendRatio definition (the plan's "max/min of grand totals" claim at plan.md line 168 is also wrong — it's max/min of `rem`).

## Finding 4: Damping factor φ contradicts itself three times across the plan — φ=0.9 vs φ=0.98, with materially different forecasts

- **Severity:** High
- **Location:** plan.md "Risks" (line 175); phase-02 "Why OLS" (line 58); phase-02 "Implementation Steps" step 2 (line 75) + "Risk Assessment" (line 116)
- **Flaw:** The plan specifies φ three different ways: (1) plan.md line 175: "damp the trend (φ=0.9, same as the dashboard ETS)"; (2) phase-02 line 58: "`next_fitted = intercept + slope * n * φ` (φ=0.9)"; (3) phase-02 line 75: "Phi defaults to 0.98 (gentle damping — the trend is real, we don't want to suppress it)" and line 116: "φ=0.98 damping". 0.9 and 0.98 produce materially different extrapolations on a steep trend.
- **Failure scenario:** With the Ky-2 OLS slope (~75M/cycle from 80M→457M over 5 intervals), `next_fitted = intercept + slope*6*φ`. At φ=0.9: ~80M + 75M*6*0.9 = 485M. At φ=0.98: ~80M + 75M*6*0.98 = 521M. A 36M swing on a forecast where the acceptance criterion is "≥300M" — the choice of φ determines whether the band clears the bar with margin or overshoots by 14%. The implementer picks one constant; the reviewer cannot tell which the plan intends; the backtest baseline depends on the choice.
- **Evidence:** plan.md:175 ("φ=0.9"); phase-02:58 ("φ=0.9"); phase-02:75 ("Phi defaults to 0.98"); phase-02:116 ("φ=0.98 damping"). All four citations are in the same plan.
- **Suggested fix:** Pick a single φ, state it once, and make it a config field (`CashForecastConfig.TrendDampFactor`) with the chosen default. Delete the "same as the dashboard ETS" claim unless verified (the dashboard's `DampedHoltState` at `dashboard/forecasting.go:52` uses a different damping semantics — φ on the trend component in Holt's recursion, not a multiplicative scalar on the extrapolated step).

## Finding 5: Wallet demand forecast shares `forecastDemandDistributionBetween` — Phase 2's detrend branch silently alters the wallet forecast with a different `paidFrac` semantics

- **Severity:** High
- **Location:** Phase 2 (modifies `forecastDemandDistributionBetween`); plan.md "Reuse, do not rebuild" (line 118)
- **Flaw:** The plan explicitly reuses `forecastDemandDistributionBetween` for both the cash-readiness and wallet-demand forecasts (plan.md line 73: "The wallet-demand forecast reuses the same engine"). But the two callers pass different `paidFrac`: cash-readiness passes `1.0` (`cash_readiness_forecast.go:68`), wallet passes `completionRate(historical)` (0..1) (`wallet_demand_forecast.go:97-98`). Phase 2's detrend branch fits OLS on `rem` and re-trends with `nextFitted`, but the existing `pf` (paidFrac) scaling is applied AFTER gamma sampling (`wallet_demand_forecast_math.go:478`: `gammaSample(rng, shape, scale) * pf`). The detrend math operates on the PRE-`pf` `rem` values, but the re-trended output is then scaled by `pf` only inside the gamma samples — `nextFitted` is added to quantiles that were computed from `pf`-scaled samples.
- **Failure scenario:** In the wallet path, `rem` values are raw (unscaled by pf), OLS fits on raw, residuals are raw, gamma samples are scaled by pf, quantiles are pf-scaled, then `nextFitted` (raw, unscaled) is added. The re-trended p50 = `pf_scaled_detrended_p50 + raw_nextFitted` mixes scaled and unscaled quantities. For paidFrac=0.7, the gamma p50 is multiplied by 0.7 but nextFitted is not — the forecast is biased high by the unscaled trend term. The wallet forecast (a separate advisory surface) silently regresses. The plan's Risk Assessment (phase-02 line 117) claims "the comparison is self-consistent (both detrended)" but does not address the pf scaling mismatch.
- **Evidence:** `wallet_demand_forecast_math.go:478` (`gammaSample(rng, shape, scale) * pf`) and `:471-475` (degenerate path scales mean by pf). `cash_readiness_forecast.go:68` (paidFrac=1.0). `wallet_demand_forecast.go:116` (paidFrac=rate). Plan phase-02 step 4 re-trend formula: `p50 = detrended_p50 + nextFitted` — no pf on nextFitted.
- **Suggested fix:** Either (a) apply `pf` to `nextFitted` before adding (`p50 = detrended_p50 + nextFitted*pf`), or (b) document that detrending is only valid when paidFrac=1.0 and gate the detrend branch on `pf >= 1.0`, or (c) move the pf scaling outside the detrend path entirely (fit gamma on raw, scale the final p50/p95 by pf). Add a wallet-forecast test that asserts the detrend path with paidFrac=0.7 does not double-count.

## Finding 6: Phase 1 snapshot trigger `cycleDayToday == prepareByCycleDay` is a single-day equality — a missed cron/page-view on that exact day leaves NO snapshot, and the accuracy logger logs "no snapshot" forever for that cycle

- **Severity:** High
- **Location:** Phase 1, "Implementation Steps" step 3 (line 82) + "Risk Assessment" (line 107)
- **Flaw:** Step 3 says "if `cycleDayToday == prepareByCycleDay`, write the P50/expected to Redis." `prepareByCycleDay` is not a field that exists in the codebase (grep returns nothing for `prepareByCycleDay`/`PrepareByCycleDay`). `PrepareByDate` returns a `time.Time` (pay date − leadDays), not a cycle-day index. Even if mapped, the equality `cycleDayToday == prepareByCycleDay` is a single calendar day. The Risk Assessment acknowledges "If the admin doesn't open the page on the prepare-by date, no snapshot is written" and proposes "a cron job writes the forecast snapshot every cycle-day during the prepare window" — but that cron job is not in the Implementation Steps, has no file assignment, and the existing scheduler infrastructure (`scheduler_jobs.go`) is not referenced.
- **Failure scenario:** Ky-2 prepare-by date = 2026-07-15 (pay 17th, lead 2). The admin opens the dashboard on the 14th (early) and 16th (late) but not the 15th. No snapshot is written. On 2026-07-18, the accuracy asynq task fires, reads Redis, finds nothing, logs "no snapshot for Ky-2/2026-07." That cycle's accuracy is permanently lost. The Phase 4 UI shows "chưa đủ dữ liệu" for 4 cycles instead of 3. The ML-escalation trigger (needs 4 cycles of data) is delayed by one full cycle. Over a year, roughly 1 in 4 cycles may be missed (prepare-by falls on a weekend/holiday/inattention).
- **Evidence:** Plan phase-01:82 ("if `cycleDayToday == prepareByCycleDay`"). Grep for `prepareByCycleDay`/`PrepareByCycleDay` in codebase: zero hits. `backend/internal/pkg/clock/pay_cycle.go:191-196` (`PrepareByDate` returns `time.Time`, not a cycle-day). The Risk Assessment's "cron job" mitigation (line 107) has no corresponding Implementation Step. Scheduler infra: `backend/internal/app/bootstrap/scheduler_jobs.go` (cron via `scheduler.Scheduler`, not asynq).
- **Suggested fix:** Define a prepare-by WINDOW (e.g., cycle-day range `[prepareByCycleDay-2, prepareByCycleDay]`), write/overwrite the snapshot on every `GetCashReadiness` call within that window, AND add a scheduler job (in `scheduler_jobs.go`, not asynq) that writes the snapshot daily during the window independent of page views. Replace the `prepareByCycleDay` symbol with the actual `PrepareByDate`-derived cycle-day, or compute it from `NextTimesheetPayCycle`.

## Finding 7: Phase 1 step 5 schedules an asynq task "for days 11, 18, 25, 2" — these are not valid asynq schedules and the day-2 case crosses month boundaries the plan doesn't handle

- **Severity:** Medium
- **Location:** Phase 1, "Implementation Steps" step 5 (line 90)
- **Flaw:** Step 5 says "add an asynq task `cash_readiness:accuracy` scheduled for 1 day after each pay date (days 11, 18, 25, 2)." Asynq's scheduler uses crontab or `@every` specs (see `mux.go:73,89,102,122,138`). "Days 11, 18, 25, 2" is not a valid crontab field (crontab day-of-month is 1-31; multiple days need a list `2,11,18,25`). More importantly, Ky-4 pays on day 1 of the NEXT month — "day 2" in the work month is the wrong month's Ky-4. The task must fire on day 2 of the month AFTER the work month, with the `{ky, month}` key pointing back to the PRIOR month's Ky-4. The plan gives no logic for this.
- **Failure scenario:** The cron `2,11,18,25 * * *` fires on the 2nd of every month. On 2026-08-02, it should read the snapshot for Ky-4/2026-07 (work month July, pay date Aug 1). But the Redis key `cash_readiness:forecast:{ky}:{yyyy-mm}` — what `{yyyy-mm}` does the task use? If it uses "today's month" (2026-08), it reads the wrong key (no snapshot exists for Ky-4/Aug because Ky-4/Aug hasn't paid yet). If it uses "last month" (2026-07), it must special-case Ky-4. The plan does not specify. Result: Ky-4 accuracy is either never logged (wrong key) or logs against a stale/missing snapshot.
- **Evidence:** Plan phase-01:90 ("days 11, 18, 25, 2"). `backend/internal/pkg/clock/pay_cycle.go:90-93` (Ky-4 `PayDate` = day 1 of next month). `backend/internal/infra/asynq/mux.go:122` (crontab spec `"1 0 * * *"` — the pattern asynq expects). No existing asynq task uses a "day-of-month list" schedule; the project's cron jobs use single day-of-month or `@every`.
- **Suggested fix:** Use four separate crontab entries (`11 0 * * *`, `18 0 * * *`, `25 0 * * *`, `2 0 * * *`) each enqueuing a task with the explicit `{ky, workMonth}` payload computed by the scheduler (not derived inside the handler from `clock.Now()`). For the day-2 entry, set `workMonth` = previous month and `ky=4`. Document the month-rollover logic.

## Finding 8: Accuracy logger writes to `logs/cash-readiness-accuracy.jsonl` with concurrent appends from a fire-and-forget goroutine — no file locking, no atomic write, corrupted lines on crash mid-write

- **Severity:** Medium
- **Location:** Phase 1, "Implementation Steps" step 4 (line 88) + "Non-functional" (line 30: "fire-and-forget (non-blocking goroutine)")
- **Flaw:** The logger appends JSON-lines to `logs/cash-readiness-accuracy.jsonl` from a fire-and-forget goroutine. The plan specifies monthly rotation but no write synchronization. If the goroutine crashes mid-`Write` (OOM, panic, signal), the file contains a partial JSON line. The Phase 4 accuracy endpoint (phase-04 step 2) "Reads the last N entries from `logs/cash-readiness-accuracy.jsonl`" — a truncated line breaks the JSON parser, and depending on the parser, either drops all subsequent entries or returns an error to the endpoint. There is also no `O_APPEND|O_CREATE` open-mode specified, and no handling of the case where the log directory doesn't exist (the `logs/` dir exists today per `ls backend/logs`, but deployment environments may differ).
- **Failure scenario:** The asynq handler calls `LogForecastAccuracy` which spawns a goroutine that opens the file and writes a ~200-byte JSON line. The process receives SIGTERM mid-write (deploy rolling restart). The file ends with `{"ky":2,"month":"2026-07","forecast_p50":314000000,"forecast_expected":3310000` — truncated. On the next accuracy read, the endpoint's `json.Decoder` returns `unexpected EOF` on the last line. The Phase 4 card shows no accuracy data ("chưa đủ dữ liệu") even though 3 valid cycles exist above the corrupt line. The lumberjack dependency exists in go.mod but the plan never references it for rotation.
- **Evidence:** Plan phase-01:88 (appends to JSONL). Plan phase-01:30 ("fire-and-forget (non-blocking goroutine)"). `backend/go.mod:38` (`gopkg.in/natefinch/lumberjack.v2 v2.2.1` — available but unused by the plan). Existing log dir: `backend/logs/` contains `app.log`, `onepay-webhook.log`, `payment-gateway.log` (file-logger pattern at `container.go:354`). No existing service writes raw JSONL without lumberjack.
- **Suggested fix:** Use lumberjack for rotation + write each line with `O_APPEND|O_CREATE|O_WRONLY` and a single `file.Write(append(line, '\n'))` call (atomic on POSIX for small writes under PIPE_BUF). Before reading in the accuracy endpoint, scan-and-skip lines that fail `json.Unmarshal`, and log a count of skipped corrupt lines. Better: use Redis (the snapshot store is already Redis) for the accuracy log too — atomic `RPUSH` avoids all file-corruption surface.

## Finding 9: Phase 3 `growthEWMA` on `grandTotals` uses `last 3 pairs` but the cohort may have 6 cycles — the EWMA seed and the "last 3" window are undefined for n<4

- **Severity:** Medium
- **Location:** Phase 3, "Implementation Steps" step 4 (line 99-102) + "Architecture" (line 44-46)
- **Flaw:** The growth EWMA helper `growthEWMA(grandTotals []int64, alpha float64)` is specified as "Compute MoM growth rates from the last 3 pairs. Apply EWMA: `ewma = α*latest + (1-α)*prev`." With 6 grandTotals there are 5 growth-rate pairs; "last 3" = pairs [3,4,5]. But the EWMA recursion `ewma = α*latest + (1-α)*prev` needs a SEED value for `prev` — the plan never defines it. Is `prev` seeded to the first of the 3, or to the EWMA of all prior pairs, or to 1.0? Also, when `len(grandTotals) < 4` (fewer than 3 pairs), the "last 3 pairs" is undefined. Phase 1's walk-forward backtest forecasts cycle i=1 (the 2nd cycle) from cycles[0..0] — a 1-element basis. At that point `grandTotals` has length 1, zero growth pairs, and `growthEWMA` must return something (1.0? the plan doesn't say). Phase 3's "delegate to inner provider when trendRatio < cutoff" does not cover this because trendRatio is undefined (min=max, ratio=1.0 < 3.0) so it delegates — but only if the detrend branch is also gated on the same cutoff.
- **Failure scenario:** Walk-forward backtest, forecasting the 3rd cycle from 2 priors. `grandTotals = [80M, 130M]`, one growth pair (+62%). "Last 3 pairs" = 1 pair. `growthEWMA` returns... undefined. If the implementer seeds `prev=1.0`, EWMA = 0.5*1.62 + 0.5*1.0 = 1.31, growthP50 = 130M*1.31 = 170M. If seeded to the first pair (1.62), EWMA = 1.62. Different answers, no spec. The backtest baseline (Phase 1 success criterion) depends on this choice.
- **Evidence:** Plan phase-03:99-102 (no seed definition). Plan phase-03:44-46 ("recentGrowthRates = [grandTotals[i]/grandTotals[i-1] for last 3 pairs]"). `backend/internal/app/services/cash_readiness_backtest_test.go:71` (`for i := 1; i < len(cycles); i++` — forecasts from i=1 with a 1-element basis).
- **Suggested fix:** Specify the EWMA seed explicitly (e.g., seed = first growth rate in the window, or seed = 1.0 meaning "no growth"). Specify behavior when `len(pairs) < 3` (use all available pairs, or return 1.0 and delegate). Add a test for `growthEWMA` with n=1, n=2, n=6 grandTotals.
