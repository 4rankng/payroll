# Red Team Review — Scope & Complexity Critic (Contract Verifier)

Plan: trend-aware-cash-forecast
Reviewer role: CONTRACT VERIFIER + YAGNI/scope enforcement
Verdict: BLOCK. The plan's central data-flow premise is contractually false against the code (Finding 1), and 3 of 4 phases are gold-plated for a 6-point series.

---

## Finding 1: The plan fits gamma on the wrong series — the "detrend residuals" premise is contractually impossible as drawn

- **Severity:** Critical
- **Location:** Plan `## Architecture`, `## Data flow change`; Phase 2 `## Architecture` and Implementation Step 4.
- **Flaw:** The entire plan is justified by the claim that the deployed engine "fits a gamma distribution to the **grand totals**" (plan.md L21, L34) and that Phase 2 will "fit OLS on the per-cycle remaining values (`rem`, not grand totals)" (phase-02 step 4). The actual code does neither thing the plan describes consistently. `forecastDemandDistributionBetween` builds `rem[]` as the **remaining demand in the forecast window per historical cycle** (`endAmount − cumulativeAt(fromCycleDay)`, wallet_demand_forecast_math.go:431-437), then fits gamma on `rem` (line 463). It never fits on grand totals. The plan's headline "198M mean dominated by averaging effect" narrative describes averaging 6 grand totals — but that is not what the function computes. The function computes the *delta* between two cycle-day positions, which for the backtest equals "accrual after cycle-day 3 through pay date."
- **Failure scenario:** Phase 2 step 4 says "Fit OLS on the per-cycle remaining values (`rem`, not grand totals)" — but the very next bullet says "Re-trend: `p50 = detrended_p50 + nextFitted`" where `nextFitted = intercept + slope*n`. If OLS is fit on `rem` (windowed deltas), then `nextFitted` extrapolates the *delta* trend, and adding it to `detrended_p50` (also a delta) double-counts the trend. If instead OLS is meant to be fit on grand totals (as the Architecture diagram shows), then Phase 2 step 4 directly contradicts the diagram. The plan cannot decide what series it operates on because the author conflated `grandTotal` (the cohort field) with `rem` (the gamma input). The first implementer will pick one reading; the backtest will silently validate the wrong transform.
- **Evidence:** `backend/internal/app/services/wallet_demand_forecast_math.go:426-463` (rem built from windowed delta, not grand totals; gamma fit on rem at :463); `backend/internal/app/services/cash_readiness_forecast.go:68` (paidFrac=1, so rem IS the cash figure — but it's still a windowed delta, not a grand total); plan.md:21,34 ("fits a gamma distribution to the grand totals" — false); phase-02 step 4 ("Fit OLS on the per-cycle remaining values (`rem`, not grand totals)" — contradicts Architecture diagram which detrends grand totals).
- **Suggested fix:** Pick exactly one series and state the invariant explicitly. If detrending grand totals, the windowed-delta math in `forecastDemandDistributionBetween` must be re-derived end-to-end (the delta of a trend is not the trend of a delta). If detrending `rem`, re-trend must multiply, not add (`(detrended_p50 + mean_residual) × growth_factor`), and the plan's additive `+ nextFitted` formula is wrong. Either way this is a redesign, not an implementation step.

## Finding 2: The plan duplicates a Damped Holt forecaster that already exists and already has OLS

- **Severity:** High
- **Location:** Phase 2 `## Architecture` ("Why OLS and not Damped Holt's") and Implementation Step 1 (`olsFit`).
- **Flaw:** The plan argues OLS is preferable to the dashboard's Damped Holt because Holt "needs ≥2 passes + walk-forward state," then writes a brand-new `olsFit` helper. The dashboard forecaster already contains a closed-form OLS routine (`initializeDampedHolt`, forecasting.go:60-98, identical `sumX/sumY/sumXY/sumX2/denominator` math), already has φ damping (forecasting.go:39, Phi=0.90 — the exact value the plan's Risks section cites), already has MAPE calculation (`calculateMAPE`, forecasting.go:204), and already has walk-forward parameter optimization (`optimizeParameters`, forecasting.go:147). The plan re-implements all four primitives from scratch in a different package.
- **Failure scenario:** Two divergent forecasting codebases coexist. The dashboard team tunes φ/α/β; the cash-readiness team has its own `olsFit` + φ=0.98 hardcoded (phase-02 step 2 — note: φ=0.98 here directly contradicts φ=0.9 stated in plan.md Risks L175). Bug fixes in one never propagate to the other. The "reuse, do not rebuild" section (plan.md:117) is violated by the plan's own Implementation Steps.
- **Evidence:** `backend/internal/app/services/dashboard/forecasting.go:60-98` (OLS init), :103-143 (DampedHoltForecast with φ), :147-201 (walk-forward optimization), :204-223 (MAPE); plan.md:175 ("φ=0.9, same as the dashboard ETS") vs phase-02 step 2 ("Phi defaults to 0.98"); plan.md:117 ("Reuse, do not rebuild").
- **Suggested fix:** Either (a) extract the dashboard's OLS + Holt into a shared `forecasting` package and consume it here, or (b) drop the entire detrend+blend machinery and call `HoltWintersForecaster.Forecast(grandTotals, 1, config)` directly — it already returns point + confidence interval. The "confidence interval" is the band; no gamma MC needed.

## Finding 3: `cohortSeries` is unexported — the TrendAwareAccrualProvider cannot live in a separate file/package as drawn, and the "drop-in" claim is misleading

- **Severity:** High
- **Location:** Phase 3 `## Architecture`, `## Related Code Files` (Create: `trend_aware_provider.go`); Phase 1 fixtures ("`[]cohortSeries`").
- **Flaw:** The `ForecastProvider.ProjectAccrual` signature takes `hist []cohortSeries` (cash_readiness_forecast.go:35). `cohortSeries` is a lowercase, unexported struct in `package services` (wallet_demand_forecast_math.go:25). The plan's Phase 3 says the new provider "implements `ForecastProvider`" and Phase 1 says fixtures are "the same type `buildTimesheetCohort` produces" (`[]cohortSeries`). This only compiles if `trend_aware_provider.go` lives in the *same* `package services`. But the plan presents it as an isolated, swappable, DI-wired component ("a new `TrendAwareAccrualProvider` implements it, wrapping the existing `TimesheetAccrualProvider`"). The forecast snapshot store (Phase 1 step 3) and the accuracy logger also need to serialize/compare `cohortSeries` grand totals — which means either exporting the type (ripple across the codebase) or duplicating the struct shape in fixtures (drift risk).
- **Failure scenario:** The provider must be wired in `services/init.go:514` where `NewCashReadinessForecastService(..., nil, clk, cfg.CashForecast)` is currently called with `nil` provider. The plan says (Phase 3 step 6) to "swap in `container.go`" — but the wiring is in `services/init.go`, not `container.go`. The implementer following the plan edits the wrong file. Separately, fixtures serialized as JSON cannot round-trip into `cohortSeries` without a custom marshaller because `dailyAmount`/`cumulative` are `map[int]int64` — the plan's "extract fixtures to JSON" step (Phase 1 step 1) is underspecified.
- **Evidence:** `backend/internal/app/services/wallet_demand_forecast_math.go:25` (`type cohortSeries struct` — lowercase); `backend/internal/app/services/cash_readiness_forecast.go:34-36` (interface uses `[]cohortSeries`); `backend/internal/app/bootstrap/services/init.go:514` (actual wiring location, `nil` provider); phase-03 step 6 ("Modify `container.go`" — wrong file).
- **Suggested fix:** Either keep everything in `package services` and stop describing it as a cross-package drop-in, or export `CohortSeries` and update the interface in the same diff. Fix the file path in Phase 3 (`services/init.go`, not `container.go`). Specify the fixture format explicitly (it must reconstruct `dailyAmount` + `cumulative` maps or the cohort math breaks).

## Finding 4: Three new tuning knobs on a 6-point series — the blend is unfalsifiable

- **Severity:** High
- **Location:** Phase 3 `## Requirements` (w₁=0.6, w₂=0.4, α=0.5), `## Risk Assessment` ("Three knobs on 6 data points risks overfitting"); plan.md `## Risks`.
- **Flaw:** The plan acknowledges the overfitting risk ("Three knobs on 6 data points risks overfitting") then proceeds anyway, justifying the weights by citing the Phase 1 backtest. But the backtest (plan.md table) was run *once* on 5 forecastable cycles (Jan-Jun, walk-forward), and the "best" method (D, 28.6%) beats the second-best (B, 29.3%) by 0.7 percentage points — well inside the noise floor for n=5. The blend weights 0.6/0.4 and α=0.5 are presented as backtest-validated but the backtest cannot distinguish 0.6/0.4 from 0.5/0.5 or 0.7/0.3 at n=5. The new config fields `BlendWeightGamma` and `GrowthEWMAlpha` (phase-03 step 1) add env-tunable surfaces with no validated defaults. Worse, the plan adds validation rules ("`BlendWeightGamma` in [0, 1], `GrowthEWMAlpha` in (0, 1]") but the existing `CashForecastConfig.validate` path (config.go:640-665) has no hook for these — the plan doesn't specify where validation lands.
- **Failure scenario:** After deploy, someone tunes `BLEND_WEIGHT_GAMMA=0.3` because July came in high. The next month reverts to the mean and the forecast undershoots. With 3 knobs and 1 new data point per month, the team can always rationalize a re-tune post-hoc. The "Phase 1 accuracy logger" (the stated mitigation) produces 1 observation/month — statistically meaningless for 3 parameters. This is the definition of an unfalsifiable model.
- **Evidence:** plan.md:42-47 (backtest table, n=5, methods D vs B differ by 0.7pp); config.go:217-222 (current `CashForecastConfig` has 4 fields, no Blend/Alpha); config.go:640-665 (validate() — no mention of the new fields); phase-03 step 1 (adds fields, claims validation but no location).
- **Suggested fix:** Drop the blend entirely. The backtest shows methods B, D, E, F are statistically indistinguishable (28.6-31.4%). Pick one (the simplest: EWMA growth-rate × last, method F, no blend). One knob (α), one method, one config field. If accuracy data over ≥8 cycles later justifies blending, add it then.

## Finding 5: Phase 1 is gold-plating — asynq jobs + Redis snapshots + JSON-lines logger for what a log statement achieves

- **Severity:** High
- **Location:** Phase 1 `## Architecture`, Implementation Steps 3-5, `## Success Criteria`.
- **Flaw:** Phase 1 introduces: (a) a Redis forecast-snapshot store (`cash_readiness:forecast:{ky}:{yyyy-mm}`, 30-day TTL), (b) a new asynq task `cash_readiness:accuracy` scheduled on 4 pay dates, (c) a JSON-lines log writer with monthly rotation, (d) a cron job to backfill snapshots "independent of page views." This is four new infrastructure components to produce one number per month: `|forecast − actual| / actual`. The backtest test (Phase 1 steps 1-2) already produces the accuracy number deterministically from fixtures — the live logger is a parallel, weaker signal (1 obs/month, and per the plan's own risk: "Redis snapshot missed" if the admin doesn't open the page).
- **Failure scenario:** The asynq task is scheduled "1 day after each pay date (days 11, 18, 25, 2)" — but the codebase's existing scheduler uses `ReminderDays: []int{8,15,22,-2}` (config.go:407) and pay-cycle dates are derived from `clock.NextTimesheetPayCycle`, not hardcoded day-of-month. Hardcoding day numbers duplicates the clock model and will drift when months have 28/29/30/31 days. The Redis snapshot is written "after each `GetCashReadiness` call if `cycleDayToday == prepareByCycleDay`" — but `GetCashReadiness` is called on every page view, and `prepareByCycleDay` is never defined in the codebase (the plan invents the symbol). A grep for `prepareByCycleDay` / `cash_readiness:forecast` returns zero hits.
- **Evidence:** phase-01 steps 3-5; config.go:405-407 (existing scheduler days, different scheme); `grep -rn "cash_readiness:forecast\|prepareByCycleDay"` → 0 hits; `grep -rln asynq backend/internal/app/workers/` shows 8 existing workers — adding a 9th for a 1-number/month signal.
- **Suggested fix:** Cut Phase 1 to: (1) the fixture-backed backtest test (already 90% written per the existing `cash_readiness_backtest_test.go`), and (2) a single `slog.Info("forecast_accuracy", ...)` line emitted when actuals become available. No Redis, no asynq, no JSON-lines. If structured querying is later needed, migrate the log then.

## Finding 6: Phase 4 (trend UI) is scope creep — unvalidated admin need, and the accuracy data source doesn't exist yet

- **Severity:** Medium
- **Location:** Phase 4 `## Requirements`, `## Architecture` (new `/accuracy` endpoint), `## Related Code Files` (8 files touched).
- **Flaw:** Phase 4 adds a growth-rate badge, a trend-adjusted badge, a rolling-accuracy footer, a new HTTP endpoint (`GET /cash-readiness/accuracy`), a new React Query hook, a new handler, a new route registration, and a new TS type — 8 file modifications. The justification is "the admin can see *why* the number is what it is." No evidence is cited that the admin requested this, and the plan's own Risk Assessment (plan.md:176) admits "If July reverts to ~250M, the growth-adjusted forecast overshoots" — i.e., the growth-rate badge may display a misleading "+90% trend" right before a mean reversion. The accuracy footer reads from the JSON-lines log that Phase 1 produces — but the plan admits (Phase 4 Risk) it will show "chưa đủ dữ liệu" for the first 4 cycles, i.e., until ~November 2026. That's 4 months of UI surface carrying a null state for a feature no one asked for.
- **Failure scenario:** The new `/accuracy` endpoint must read `logs/cash-readiness-accuracy.jsonl` (Phase 4 step 2) — but reading a log file from an HTTP handler introduces a filesystem dependency on a rotated log, which races with the log rotator and breaks under containerized deployments where `logs/` may be ephemeral. The existing `logs/` dir contains only `app.log`, `onepay-webhook.log`, `payment-gateway.log` — no JSON-lines pattern exists in the codebase, so there is no rotation infrastructure to reuse.
- **Evidence:** phase-04 steps 1-2, Related Code Files (8 files); `ls backend/logs/` (3 plain-text logs, no jsonl, no rotation helper); plan.md:176 (overshoot risk); phase-04 Risk ("chưa đủ dữ liệu" for 4 cycles).
- **Suggested fix:** Drop Phase 4 entirely from this plan. The confidence label already exists (`confidenceLabel`, wallet_demand_forecast_math.go:541) and already downgrades on high `trendRatio`. If a trend badge is later validated as a real admin need, ship it as a separate plan once Phase 1 has ≥4 cycles of real accuracy data.

## Finding 7: The `divergent` flag interaction with detrending is hand-waved and will silently change semantics

- **Severity:** Medium
- **Location:** Phase 2 `## Risk Assessment` ("Detrending changes the divergence detection"); plan.md:178.
- **Flaw:** The current `divergent` flag (wallet_demand_forecast_math.go:495) compares gamma `p95` to `empiricalMaxCash` (both on `rem`). After detrending, the plan says both move to residuals — "self-consistent." But `newsvendorRecommendation` (line 530) uses `divergent` to floor the recommendation at `empiricalMax`: `rec = max(rec, dist.empiricalMax)`. After re-trending, `empiricalMax` is still a *residual* max (small), while `rec` is a *re-trended* value (large). The floor becomes meaningless, OR if `empiricalMax` is also re-trended, the plan never says so. Either way, the divergence safety net silently breaks.
- **Failure scenario:** Post-deploy, a cycle comes in with a genuine outlier (like June 457M). The `divergent` flag was the mechanism that prevented the gamma p95 from under-representing the observed tail. After this plan ships, `divergent` either never fires (because residual max is tiny relative to re-trended p95) or fires on noise. The newsvendor recommendation quietly loses its empirical floor, and the cash-readiness band understates the tail risk — the exact failure mode the flag was added to prevent.
- **Evidence:** `backend/internal/app/services/wallet_demand_forecast_math.go:492-495` (divergent definition on rem-space), :530-532 (`rec = max(rec, dist.empiricalMax)` — uses empiricalMax as floor); phase-02 Risk ("both are now on residuals ... self-consistent" — but `newsvendorRecommendation` mixes spaces).
- **Suggested fix:** Specify exactly how `empiricalMax` and `divergent` are re-trended, and audit `newsvendorRecommendation` end-to-end. Add a test asserting the empirical floor still engages after detrending on the Ky-2 fixture.

## Finding 8: Acceptance criterion "July Ky-2 forecast ≥300M" is a hard-coded target that encodes the overfit

- **Severity:** Medium
- **Location:** plan.md `## Acceptance criteria` ("July Ky-2 forecast ... ≥300M"); Phase 2 & 3 Success Criteria repeat it.
- **Flaw:** The plan's own backtest (plan.md:47) shows the *best* method (F) forecasts 314M for July Ky-2 against an actual of 457M — and admits "even the best method misses June by ~30%." Setting ≥300M as the acceptance criterion bakes in the assumption that July ≥ June. But Risk (plan.md:176) explicitly considers "If July reverts to ~250M." If July actual is 250M and the forecast is 300M (passes acceptance), the forecast is 20% high — yet the plan declares success. The acceptance criterion measures "did we move the number up," not "are we accurate."
- **Failure scenario:** Phase 3 ships, July forecast = 310M (acceptance passed), July actual = 240M. The plan is "done" by its own criteria while being 29% wrong in the direction the backtest said was risky. The accuracy logger (Phase 1) catches this one month later, but the plan has already landed.
- **Evidence:** plan.md:168 ("≥300M"); plan.md:47 (best method 314M vs 457M, 31% low); plan.md:176 (reversion to 250M scenario); phase-02/03 Success Criteria repeat ≥300M.
- **Suggested fix:** Replace the hard-coded ≥300M criterion with: "walk-forward backtest mean abs % error ≤ baseline − 10pp" (already in the criteria) and drop the absolute-forecast target entirely. An absolute forecast number is not an accuracy measure.

## Finding 9: The "no schema migration" constraint conflicts with the structured-accuracy-querying escape hatch

- **Severity:** Medium
- **Location:** plan.md `## Constraints` ("No schema migration unless required"); Phase 1 `## Requirements` ("No new DB table unless accuracy data needs structured querying (deferred)").
- **Flaw:** The plan defers the DB-table decision but builds an architecture (Redis snapshots + JSON-lines + asynq) that only makes sense if you *don't* need structured querying. If you later need structured querying (the explicit escape hatch), none of the JSON-lines/Redis work is reusable — you migrate to a table and throw away the logger. The plan is paying the integration cost of two architectures to get the value of neither.
- **Failure scenario:** Three months in, someone wants "accuracy by Ky over time" on the dashboard. The JSON-lines log can't be queried; the team adds a table. The Redis snapshot store, asynq task, and log writer are all deprecated. The "deferred" decision was never made — it was avoided.
- **Evidence:** plan.md:156; phase-01 Requirements NFR.
- **Suggested fix:** Decide now. If accuracy is "a number the engineering team checks," use `slog` (no infrastructure). If accuracy is "an admin-facing metric over time," add a `forecast_accuracy` table now and skip Redis/JSON-lines entirely. The middle ground is the worst option.

## Finding 10: The minimum viable fix is one helper function — the 4-phase plan is 4× over-scoped

- **Severity:** Medium (scope, not correctness)
- **Location:** Entire plan structure (4 phases, M+L+M+M effort).
- **Flaw:** The plan's own backtest (plan.md:42-47) shows method F (EWMA growth-rate × last actual) achieves 31.0% error — within 2.4pp of the best blend (D, 28.6%) — and requires zero new structs, zero new providers, zero new config knobs beyond α. The minimum viable fix is: (1) in `confidenceLabel`'s `trendRatio >= trendRatioCutoff` branch, instead of just downgrading confidence, multiply the returned quantiles by `growthEWMA(grandTotals, α)`. That's one helper (~15 lines), one config field (`GrowthEWMAlpha`), one test. The 4-phase plan (detrend struct fields + TrendAwareAccrualProvider + accuracy harness + UI) is 4-6× the code for a 2.4pp backtest delta that is inside the noise.
- **Failure scenario:** The plan consumes M+L+M+M engineering effort across 4 sequential phases with a hard dependency chain (1→2→3→4). Any slip in Phase 1 (fixtures, asynq) blocks Phase 2 (the actual fix). The triggering problem (July Ky-2 = 198M) is not addressed until Phase 3 lands. The MVP (method F inline) could ship in one PR.
- **Evidence:** plan.md:42-47 (F=31.0% vs D=28.6%, Δ=2.4pp on n=5); plan.md:149-151 (4 phases, linear dependency); wallet_demand_forecast_math.go:541-561 (the single function where the trend-aware branch would live).
- **Suggested fix:** Cut to a single phase: add `growthEWMA` helper, call it in the `trendRatio >= trendRatioCutoff` branch of the existing pipeline, expose `growth_rate` in the existing DTO. Defer the detrend engine, the blend provider, the accuracy harness, and the UI to a follow-up plan gated on ≥6 months of real accuracy data showing the MVP is insufficient.
