**Test Dimensions:**

The agent covers three dimensions based on $OBJECTIVE. Not every run needs all three — the $OBJECTIVE decides emphasis.

### Dimension A: Visual Elegance (Desktop)
- Layout: no overflow, proper spacing, consistent alignment
- Typography: readable font sizes (≥14px body), proper hierarchy
- Components: cards, tables, forms render correctly at 1440px
- Touch/click targets: buttons ≥36px, icons properly sized
- Consistency: colors, spacing, borders follow design system

### Dimension B: Visual Elegance (Mobile — 375px)
- Same checks as Desktop but at mobile viewport
- Additionally: sidebar hidden/collapsible, content fills width, no horizontal scroll
- Touch targets: all interactive elements ≥44px (Apple HIG) or ≥36px (acceptable minimum)
- Bottom nav (driver/forwarder) properly rendered
- Forms: inputs usable, labels visible, no cramped fields
- Tables: either responsive cards or horizontally scrollable with sticky first column

### Dimension C: Business Flow Correctness
- Read the relevant flow doc from `docs/flows/`
- Test each user story against acceptance criteria in `PRODUCT-SPECS.md`
- Verify calculations (salary, cost, revenue, profit) against spec formulas
- Verify role-based access (who can see/do what)
- Verify status transitions and their side effects (lock → ledger entry, etc.)
- Verify data persistence (create → save → reload → verify)
- Edge cases: zero values, missing fields, concurrent states

**Execution Workflow (The Micro-Iteration Loop):**

**Phase 0: Scope Definition (Lead QA Engineer — Run Once)**
1. Read $OBJECTIVE.
2. Parse which dimensions (A/B/C) are in scope.
3. If Dimension C is in scope: read relevant flow docs from `docs/flows/` that match the objective.
4. Generate a lightweight "Test Execution Checklist" breaking the work into granular, single-area items. Each item specifies:
   - Which role(s) to test with
   - Which viewport(s) (desktop, mobile, or both)
   - Which dimension(s) (visual desktop, visual mobile, business flow)
   - Which flow doc page applies (if any)
5. Write the checklist to `qa/run-checklist.md` for persistence across /compact cycles.
6. Select the first incomplete item and begin Phase 1.

**Phase 1: Focused QA Testing (Lead QA Engineer)**
1. Authenticate into $HOST using ONLY the account relevant to the current checklist item.
2. Set the correct viewport(s) for this item.
3. Test ONLY the specific area/flow — no scope creep.
4. **Hard Cap:** Stop testing once you have identified a maximum of **3 bugs or issues** across all dimensions for this item.
5. Generate a brief "Micro-Bug Report." If no bugs found, mark the item as "Passed" on the checklist and restart Phase 1 with the next item.

**Phase 2: Micro-Patching (Senior Software Engineer)**
1. Review the current "Micro-Bug Report."
2. Formulate and apply the minimum necessary code changes to fix ONLY the reported issues.
3. Run `tsc --noEmit` to verify no type errors introduced.
4. Respond with a concise "Patch Report" detailing files changed, and hand back.

**Phase 3: Verification & Advancement (Lead QA Engineer)**
1. Review the "Patch Report."
2. Re-test the specific bugs that were fixed on the SAME viewport(s).
3. If resolved, mark the current item as "Passed," update `qa/run-checklist.md`, and loop to Phase 1 for the next item.
4. If bugs remain, generate a new "Micro-Bug Report" and return to Phase 2.

**Context Management Rule:**
- After every `$COMPACT_EVERY` iterations, save current progress to `qa/run-checklist.md` and run `/compact`.
- The checklist file is the single source of truth — it survives context compaction.
- On recovery from /compact, read `qa/run-checklist.md` first to resume.

**Exit Condition:**
Strictly loop Phases 1–3 until every item on the "Test Execution Checklist" is marked "Passed." Once complete, output the "Final QA Sign-Off."
