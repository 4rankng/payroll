# Feature: Salary Disbursement

Salary disbursement turns approved timesheets into money in employee bank accounts. It is a multi-stage pipeline that runs weekly per project, with several layers of recovery so a stuck batch can always be re-driven without double-paying. The wallet is the funds source; the active payment provider (OnePay in production, 9Pay in sandbox) is the transport.

## Pipeline overview

```
admin export (.xlsx "Yêu cầu chuyển tiền")
       │
       ▼
wallet_bulk.booking  ────► BulkTransferBatch (status: pending → processing)
       │                              │   enqueue: pending → enqueued
       │                              ▼
       │              wallet_bulk_transfer_row_worker (per row)
       │                              │
       │                              ▼
       │              disbursement.execute → wallet_payment (pending)
       │                              │
       │                              ▼
       │              provider API call (OnePay/9Pay)
       │                              │
       │                              ▼
       │              IPN webhook → ipn:process worker → wallet state machine
       │                              │
       │                              ▼
       │              completed | failed | reversed
       │                              │
       ▼                              ▼
verified_transfer_recovery  ◄───  batch reaches success_count + failed_count == total_count
       │
       ▼
batch: completing → book_batch_ledger → completed | failed
       │
       ▼
wallet_settlement_worker  → advance_payment settlement, salary deduction
```

## Stages in detail

### 1. Admin export

`internal/app/services/payroll/` exposes the bank-transfer workbook exporter (`report_exporter.go`, `report_by_project_exporter.go`) plus PDF variants. The "Chuyển OnePay" action on `/admin/timesheet` produces a `.xlsx` file using the template generated by `excel/template.go`. The file is the contract between admin and the disbursement pipeline.

### 2. Upload and booking

Admin uploads the workbook. `internal/app/services/wallet_bulk/booking.go` parses it (`parser.go`), creates one `BulkTransferBatch` row per upload (uniqueness enforced by `content_hash`), and persists the parsed rows in the batch's `data` JSON column so the outbox sweeper and the KQ Excel generator can re-read inputs without re-parsing the workbook.

Lifecycle (`internal/domain/bulk_transfer_batch.go`):

```
pending → processing → completing → completed
                       ↘ failed
```

The `completing` state is a transient inside a `SELECT … FOR UPDATE`: once `UpdateWithLock` decides all rows are terminal, it sets the batch to `completing` and returns `shouldBook = true`, which enqueues the `book_batch_ledger` task. If the process dies between the lock commit and the ledger write, the completing-recovery cron re-attempts booking.

The batch-level outbox (`EnqueueState`):

```
pending   = batch row committed, per-row asynq tasks NOT yet enqueued (crash window)
enqueued  = all per-row tasks enqueued
```

`ListByEnqueueState(pending, olderThan)` finds batches where the outbox sweeper missed enqueueing per-row tasks. The outbox sweeper is the safety net that closes the gap between "row committed" and "row executing".

### 3. Per-row execute

`wallet_bulk_transfer_row_worker.go` processes one row at a time. Each row:

- Checks for `ErrDuplicatePaymentInProgress`, `ErrFeeResolution`, and pre-flight balance rejection — failures here decrement `total_count` atomically (`DecrementTotalCount`) so the batch can still reach the success+failed==total threshold.
- Books a `wallet_payment` row (status `pending`).
- Calls the `disbursement` service to execute via the active provider.

The disbursement registry (`internal/app/services/disbursement/registry.go`, `registry_selector.go`) picks OnePay or 9Pay at runtime based on configuration; the row worker does not need to know which is active. ADR-003 covers the abstraction.

### 4. Provider call and IPN

`disbursement_execute_worker.go` pushes the request to the provider and persists the provider invoice number. The provider sends an IPN webhook to `/api/v1/webhooks/{provider}/ipn` (IP-whitelisted). The handler verifies the signature and enqueues an `ipn:process` task.

`ipn_process_worker.go` looks up the wallet payment by invoice number, drives the wallet state machine (see `features/wallet-ledger.md`), and emits the post-commit settlement event. The wallet payment transitions through:

```
pending → verified → authorised → completed | failed | reversed
```

Only IPN-driven transitions reach terminal state in production. Polling is a safety net for missed webhooks.

### 5. Status inquiry and recovery sweepers

`disbursement_poller_worker.go` and `status_inquiry_worker.go` periodically query the provider for the status of payments that have been authorised but not yet IPN-confirmed. This catches missed webhooks (provider outage, network partition, transient 5xx).

`verified_transfer_recovery.go` and `transfer_paid_amounts.go` are recovery sweepers:

- `verified_transfer_recovery` re-attempts booking for batches stuck in `completing`.
- `transfer_paid_amounts` reconciles provider-side paid totals with local wallet payments.

These sweepers run as asynq tasks and are registered in `bootstrap/routes.go`.

### 6. Booking the ledger

When `UpdateWithLock` returns `shouldBook = true`, the batch is set to `completing` and the `book_batch_ledger` task fires. `ProcessBookBatchLedger` writes:

- The fee transaction (`total_fee`).
- The partner receivable transaction (`transfer_amount`) — only if at least one employee was paid.
- The batch status transitions to `completed` or `failed`.

`UpdateColumns` writes only the targeted columns (`total_fee`, `ledger_txn_id`, `status`) so concurrent bumps to `success_count` / `failed_count` are not clobbered.

### 7. Settlement

`wallet_settlement_worker.go` reconciles advance payments against the disbursed salary. For each wallet payment it walks the employee's open `advance_payment_request`s, marks each as settled against this salary batch, and writes the matching ledger entries. See `features/flexpay.md` for the FlexPay side.

## Provider abstraction (ADR-003)

`internal/infra/disbursement/onepay/` is the production adapter; `internal/infra/disbursement/ninepay/` is the sandbox/dev adapter. Each implements `domain.PaymentProvider` (Topup, Transfer, StatusInquiry, Cancel, IPNVerification) with its own signing, types, queue, and webhook signature verification. Production uses OnePay exclusively; the system is provider-agnostic so the swap is config-only.

`provider_transaction_service.go` is the application-level wrapper that translates between the wallet state machine triggers (`ipn_completed`, `ipn_failed`, `ipn_reversed`) and provider-specific results. `fee_schedule_service.go` owns the per-batch fee computation.

## Workers (asynq)

The pipeline is run by:

- `bulk_transfer_worker.go` — top-level orchestration per batch.
- `bulk_transfer_ninepay_execute_worker.go` — 9Pay-specific execute path.
- `bulk_transfer_transaction_worker.go` — revenue-transaction creation.
- `wallet_bulk_transfer_row_worker.go` — per-row processing.
- `disbursement_execute_worker.go` — provider execute.
- `disbursement_poller_worker.go` — provider status polling.
- `status_inquiry_worker.go` — single-payment status inquiry.
- `ipn_process_worker.go` — IPN handler.
- `wallet_settlement_worker.go` — settlement against advances.
- `verified_transfer_recovery.go` — recovery sweepers.
- `transfer_paid_amounts.go` — paid-amount reconciliation.

All are registered in `bootstrap/routes.go`. See `integrations/background-jobs.md` for the runtime details.
